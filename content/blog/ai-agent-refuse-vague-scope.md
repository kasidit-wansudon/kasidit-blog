หนึ่งในกฎแรกที่ผมใส่ไว้ใน Kasidit คือ **AI coding agent ต้องปฏิเสธ scope ที่คลุมเครือ** ฟังดูขัดกับความรู้สึก เพราะเราอยากได้ผู้ช่วยที่ "ทำให้เลย" แต่จากประสบการณ์ใช้ Claude Code ทุกวัน ผมพบว่างานที่เสียเวลาที่สุดไม่ใช่งานยาก แต่เป็นงานที่เริ่มจากคำสั่งที่ไม่ชัด แล้ว agent เดาเองว่าเราต้องการอะไร

## ปัญหาของ agent ที่ "ช่วยเกินไป"

model สมัยนี้เก่งพอจะเดาความต้องการได้ค่อนข้างแม่น ปัญหาคือ "ค่อนข้างแม่น" ไม่พอสำหรับ production code เมื่อคำสั่งคลุมเครือ agent มักทำหนึ่งในสามอย่างนี้:

1. **แก้เกิน** เห็นโค้ดข้าง ๆ ไม่สวยก็ refactor ไปด้วย diff ใหญ่ขึ้น review ยากขึ้น และเสี่ยงพังสิ่งที่ทำงานอยู่
2. **แก้ผิดจุด** แก้อาการแทนที่จะแก้สาเหตุ เช่น ใส่ null check ปิดปัญหา ทั้งที่ข้อมูลต้นทางผิด
3. **แต่งบริบทเอง** สมมติว่ามีฟังก์ชันหรือ config ที่ไม่มีอยู่จริง แล้วสร้างการแก้ไขบนสมมติฐานนั้น

ทั้งสามอย่างจบที่จุดเดียวกัน คือเราต้องเสียเวลารีวิวและย้อนแก้มากกว่าเวลาที่ agent ช่วยประหยัด

## Mission ที่ชัดหน้าตาเป็นอย่างไร

ใน Kasidit ทุกงานเริ่มจาก mission สั้น ๆ ที่มีห้าส่วน:

```text
GOAL:      ผลลัพธ์ที่ต้องการ วัดได้หรือตรวจได้
CONTEXT:   ไฟล์ / endpoint / หน้าจอที่เกี่ยวข้อง
IN SCOPE:  สิ่งที่อนุญาตให้แก้
OUT SCOPE: สิ่งที่ห้ามแตะ
DONE WHEN: เงื่อนไขที่ถือว่าเสร็จ (test ผ่าน, ผลลัพธ์ที่เห็น)
```

ถ้า agent เติมช่องใดช่องหนึ่งไม่ได้จากคำสั่งและโค้ดที่อ่าน มันต้องถามกลับ ไม่ใช่เดา นี่คือความหมายของ "ปฏิเสธ scope ที่คลุมเครือ" มันไม่ได้ปฏิเสธงาน แต่ปฏิเสธการเริ่มงานโดยไม่มีเป้าหมายที่ตรวจได้

## ตัวอย่าง: คำสั่งคลุมเครือ vs คำสั่งที่ชัด

**ตัวอย่างที่ 1: bug**

- คลุมเครือ: "หน้า orders มันช้า ช่วยดูหน่อย"
- ชัด: "หน้า `/orders` ใช้เวลาโหลดหลายวินาทีเมื่อมี filter ตามวันที่ ให้หาว่าเป็นที่ query หรือที่ frontend แก้เฉพาะ `OrderController@index` และ query ที่เกี่ยวข้อง ห้ามเปลี่ยน response format เสร็จเมื่อ query ที่ช้าใช้ index และ test ของ controller ผ่าน"

**ตัวอย่างที่ 2: feature**

- คลุมเครือ: "เพิ่ม export Excel ให้หน่อย"
- ชัด: "เพิ่มปุ่ม export รายการ `users` เป็น `.xlsx` ในหน้า admin ใช้ library ที่โปรเจกต์มีอยู่แล้ว คอลัมน์: ชื่อ, email, แผนก, วันที่สร้าง เคารพ filter ที่ใช้อยู่ในหน้า ไม่ต้องทำ export แบบ background job"

**ตัวอย่างที่ 3: refactor**

- คลุมเครือ: "clean up โค้ดส่วน payment"
- ชัด: "แยก logic คำนวณส่วนลดออกจาก `CheckoutController` เป็น class `DiscountCalculator` พฤติกรรมต้องเหมือนเดิมทุกกรณี ห้ามแก้ไฟล์อื่นนอกจากสองไฟล์นี้และ test เขียน unit test ครอบคลุมกรณีที่มีอยู่ก่อนย้าย"

สังเกตว่าคำสั่งที่ชัดไม่ได้ยาวมาก แต่ทุกคำสั่งตอบได้ว่า "เสร็จ" หน้าตาเป็นอย่างไร และ "ห้ามแตะ" อะไร

## วิธีเขียน mission ให้เร็ว

หลายคนบอกว่าเขียน mission เสียเวลา ผมเข้าใจ แต่มีทางลัด:

- **เริ่มจาก DONE WHEN** ถ้าคุณตอบไม่ได้ว่าเสร็จแปลว่าอะไร คุณเองก็ยังไม่รู้ว่าต้องการอะไร ซึ่งเป็นข้อมูลที่มีค่ามาก
- **OUT SCOPE คือส่วนที่คุ้มที่สุด** บรรทัดเดียวอย่าง "ห้ามแก้ migration เก่า" ป้องกันความเสียหายได้มากกว่าคำอธิบายยาว ๆ
- **ให้ agent ร่าง mission ก่อน** บอกเป้าหมายคร่าว ๆ แล้วให้ agent อ่านโค้ดและเสนอ mission กลับมา เราแค่ตรวจและแก้ เร็วกว่าเขียนเองทั้งหมด
- **แบ่งงานใหญ่** ถ้า IN SCOPE ยาวเกินห้าบรรทัด มักแปลว่าควรแยกเป็นหลาย mission

## Agent ควรถามกลับอย่างไร

การ "ปฏิเสธ" ที่ดีไม่ใช่การตอบว่า "ไม่ชัด ทำไม่ได้" แต่คือการถามกลับแบบที่ตอบง่าย ตัวอย่างคำตอบที่ผมอยากได้จาก agent เมื่อเจอคำสั่ง "หน้า orders มันช้า":

- ช้าตอนเปิดหน้าครั้งแรก หรือตอนกด filter
- ช้ากับผู้ใช้ทุกคน หรือเฉพาะคนที่มีข้อมูลเยอะ
- ผมอ่าน `OrderController` แล้วเห็นสอง query ที่น่าสงสัย ให้เริ่มจากจุดนี้ได้ไหม

คำถามแบบนี้สั้น มีตัวเลือก และแสดงว่า agent อ่านโค้ดมาแล้ว ไม่ใช่โยนงานกลับมาให้คนคิดทั้งหมด

## เมื่อไรที่ปล่อยให้ agent ตัดสินใจเองได้

ไม่ใช่ทุกงานต้องมี mission เต็มรูปแบบ งานที่เล็กและย้อนกลับง่าย เช่น แก้ typo เปลี่ยนชื่อตัวแปรในไฟล์เดียว หรือเขียน script ทิ้งเพื่อทดลอง ปล่อยให้ agent ทำได้เลย หลักของผมคือ ยิ่งงานกระทบหลายไฟล์ แตะข้อมูลจริง หรือย้อนกลับยาก ยิ่งต้องการ scope ที่ชัด

กฎข้อนี้คือหนึ่งในปัจจัยหลักที่ทำให้ Kasidit ได้ผลดีบน SWE-bench ซึ่งผมเล่าไว้ใน [Kasidit บน SWE-bench: จาก 63% เป็น 75%](/blog/kasidit-swe-bench-75-percent)

## สรุป

AI coding agent ที่ดีไม่ใช่ตัวที่รับทุกคำสั่งแล้วทำทันที แต่เป็นตัวที่รู้ว่าเมื่อไรควรหยุดถาม ให้ทุกงานมี GOAL, CONTEXT, IN SCOPE, OUT SCOPE และ DONE WHEN ถ้ายังเติมไม่ได้ ให้ถามก่อน แล้วคุณจะเสียเวลารีวิวน้อยลง และได้ diff ที่เล็ก อ่านง่าย และไว้ใจได้มากขึ้น
