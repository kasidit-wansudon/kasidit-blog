ปีนี้ผมย้ายการเข้าถึง SSH ของเซิร์ฟเวอร์ทั้งหมดไปไว้หลัง VPN และเปลี่ยนจากการใช้บัญชีร่วมมาเป็นบัญชีรายคน (per-engineer account) งานนี้ไม่ได้ยากในเชิงเทคนิค แต่เปลี่ยนวิธีคิดเรื่องความปลอดภัยของทีมเล็กไปเยอะมาก บทความนี้สรุปเหตุผล โครงการตั้งค่าแบบกลาง ๆ ที่ใช้ได้กับ WireGuard หรือ OpenVPN และขั้นตอน offboarding ที่ผมใช้จริง

## ทำไม SSH หลัง VPN ถึงคุ้มสำหรับทีมเล็ก

ทีมเล็กมักคิดว่า "ไม่มีใครสนใจเซิร์ฟเวอร์เราหรอก" แต่ความจริงคือ bot สแกนพอร์ต 22 ทั้งอินเทอร์เน็ตตลอดเวลา ถ้าเปิด SSH ไว้ public สิ่งที่ป้องกันเราอยู่มีแค่ key หรือรหัสผ่าน ซึ่งถ้าหลุดครั้งเดียวก็จบ

การวาง SSH ไว้หลัง VPN ให้ชั้นป้องกันเพิ่มสองชั้น:

- **ลด attack surface**: พอร์ต SSH ไม่ตอบใครเลยนอกจากคนที่อยู่ใน VPN
- **รู้ว่าใครเข้า**: ถ้าทุกคนมีบัญชี VPN และบัญชี SSH ของตัวเอง log จะบอกได้ทันทีว่าใครเข้าเครื่องไหน เวลาไหน

อีกเหตุผลที่สำคัญไม่แพ้กันคือบัญชีร่วม เช่นทุกคนใช้ `root` หรือ `deploy` ด้วย key เดียวกัน พอมีคนออกจากทีม เราต้องเปลี่ยน key ทุกเครื่อง และไม่มีทางรู้ว่า key เก่าถูก copy ไปไว้ที่ไหนบ้าง บัญชีรายคนแก้ปัญหานี้ได้ตรงจุด

## โครงสร้างโดยรวม

ภาพรวมที่ผมใช้มีแค่สามส่วน:

1. **VPN server** หนึ่งตัว ออก config ให้แต่ละคนแยกกัน (หนึ่งคน หนึ่ง profile) และเปิด MFA ถ้าระบบรองรับ
2. **Split tunnel** ส่งเฉพาะ traffic ที่ไปยัง subnet ของเซิร์ฟเวอร์เข้า VPN ส่วน traffic อื่นออกเน็ตปกติ ทีมจะได้ไม่บ่นว่าเน็ตช้า
3. **Firewall + sshd** ของแต่ละเซิร์ฟเวอร์ ยอมรับ SSH เฉพาะจาก IP ขาออกของ VPN หรือ subnet ภายในเท่านั้น

จุดที่หลายคนพลาดคือ ตั้ง firewall ตาม subnet ของ tunnel ทั้งที่ VPN บางตัวทำ NAT ก่อนส่งต่อ ทำให้เซิร์ฟเวอร์ปลายทางเห็น source IP เป็น IP ของ VPN server ไม่ใช่ IP ใน tunnel วิธีเช็กง่ายที่สุดคือต่อ VPN แล้ว SSH เข้าไปดู `who` หรือ `last` ว่าเครื่องเห็นเรามาจาก IP อะไร แล้วค่อยเขียนกฎตามนั้น

## ตัวอย่าง sshd Match rules

ผมไม่อยากปิด SSH จาก public แบบทันทีทั้งหมด เพราะถ้า VPN ล่มจะเข้าเครื่องไม่ได้เลย จึงใช้ `Match` ใน `sshd_config` จำกัดเฉพาะบัญชีของทีม ส่วนบัญชีฉุกเฉินใช้ช่องทาง console ของ cloud provider แทน

```bash
# /etc/ssh/sshd_config (ส่วนท้ายไฟล์)
PasswordAuthentication no
PermitRootLogin no

# บัญชีของทีม: ยอมรับเฉพาะจาก VPN
Match User alice,bob,carol Address 10.8.0.0/24,203.0.113.10
    AllowUsers alice bob carol

# ถ้ามาจากที่อื่น ปฏิเสธบัญชีทีมทั้งหมด
Match User alice,bob,carol Address *,!10.8.0.0/24,!203.0.113.10
    DenyUsers alice bob carol
```

ก่อน reload ให้ทดสอบ config ทุกครั้ง และเปิด session เดิมค้างไว้อีกหนึ่งหน้าต่าง กันล็อกตัวเองออกจากเครื่อง:

```bash
sudo sshd -t && sudo systemctl reload sshd
# ทดสอบจากอีก terminal ทั้งตอนต่อและไม่ต่อ VPN
ssh -v alice@server.example.com
```

ทดสอบให้ครบสองกรณี: ต่อ VPN แล้วต้องเข้าได้ ไม่ต่อ VPN แล้วต้องเข้าไม่ได้ ถ้าเช็กแค่กรณีแรก เราจะไม่รู้เลยว่ากฎทำงานจริงหรือเปล่า

## สร้างบัญชีรายคนให้เป็นระบบ

ผมเขียน checklist สั้น ๆ สำหรับ onboarding แต่ละคน:

- สร้าง VPN profile ชื่อตรงกับชื่อคน ไม่ใช้ชื่อกลางอย่าง `dev1`
- สร้าง Linux user บนเครื่องที่คนนั้นต้องใช้จริงเท่านั้น ไม่ใช่ทุกเครื่อง
- ใส่ public key ของเขาใน `~/.ssh/authorized_keys` ห้ามส่ง private key ผ่านแชต
- ให้สิทธิ์ `sudo` เฉพาะคนที่ต้อง deploy และจำกัดคำสั่งได้ก็ยิ่งดี
- จดลงตารางกลางว่าใครมีสิทธิ์อะไรบนเครื่องไหน

ตารางกลางนี้สำคัญที่สุด เพราะวันที่ต้อง offboarding เราจะไม่ต้องเดาว่าต้องไปลบอะไรที่ไหนบ้าง

## Offboarding: ตัดสิทธิ์ให้ครบในสิบนาที

เป้าหมายคือเมื่อมีคนออกจากทีม เราต้องตัดสิทธิ์ได้ครบและเร็ว ลำดับที่ผมใช้คือ:

1. **ปิด VPN profile ก่อน** ขั้นนี้ขั้นเดียวก็ตัดการเข้าถึงเครือข่ายทั้งหมดแล้ว
2. **ล็อกบัญชี Linux** ด้วย `usermod -L` และลบ key ออกจาก `authorized_keys` บนทุกเครื่องในตาราง
3. **หมุน secret ที่คนนั้นเคยเห็น** เช่นรหัส database หรือ API key ที่เคยแชร์ให้ทำงาน
4. **เก็บ home directory ไว้ก่อน** อย่าเพิ่งลบ เผื่อมีสคริปต์หรือ cron ที่ผูกกับบัญชีนั้นอยู่
5. **อัปเดตตารางกลาง** และบันทึกวันที่ตัดสิทธิ์

ผมเลือก "ล็อก" แทน "ลบ" ในวันแรกเสมอ เพราะการลบบัญชีที่มี process หรือไฟล์ผูกอยู่บางครั้งทำให้งานอื่นพังแบบไม่รู้ตัว พ้นไปสักสัปดาห์ค่อยลบจริง

## ข้อควรระวังที่เจอจริง

- **อย่าลืมช่องทางฉุกเฉิน** ถ้า VPN ล่ม ต้องมีทางเข้าเครื่องผ่าน console ของ cloud provider และต้องทดสอบให้แน่ใจก่อนว่าใช้ได้
- **VPN server คือจุดเดียวที่ต้องดูแลดีที่สุด** อัปเดตสม่ำเสมอ เปิด MFA และจำกัดหน้า admin ไม่ให้เข้าจาก public
- **web vhost กับ SSH เป็นคนละเรื่อง** การย้าย SSH ไปหลัง VPN ไม่ได้ทำให้ web app ปลอดภัยขึ้น ต้องดูแลแยกกัน
- **เขียน runbook** ตั้งแต่ขั้นตอนเพิ่มคนจนถึงตัดสิทธิ์ ผมเขียนแนวคิดนี้ไว้ใน [ทำทุก deploy ให้เป็น runbook](/blog/turn-every-deploy-into-runbook)

ถ้าอยากอ่านมุมกว้างขึ้นเรื่องบทเรียนด้านความปลอดภัยของทีมเล็ก ลองดู [บทเรียนจาก security incident](/blog/security-incident-lessons-small-team)

## สรุป

การย้าย SSH ไปหลัง VPN พร้อมบัญชีรายคนเป็นงานที่ใช้เวลาไม่กี่วัน แต่ได้ผลระยะยาว: attack surface เล็กลง รู้ว่าใครเข้าเครื่องไหน และ offboarding ทำได้ครบในไม่กี่นาที หัวใจคือทำทีละขั้น ทดสอบทั้งกรณีเข้าได้และเข้าไม่ได้ เก็บช่องทางฉุกเฉินไว้เสมอ และมีตารางกลางที่บอกว่าใครมีสิทธิ์อะไร ทีมเล็กไม่จำเป็นต้องมีเครื่องมือแพง แค่มีวินัยก็พอ
