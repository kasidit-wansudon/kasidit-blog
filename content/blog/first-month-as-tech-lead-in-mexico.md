เดือนมีนาคม 2026 ผมเริ่มงานเป็น Tech Lead ที่ OPPO Mexico ใน Mexico City ดูแลทีม 5 คน (programmer 2, QA 1, helpdesk 1, infra 1) และระบบภายในมากกว่า 6 ระบบที่มีผู้ใช้ back-office ราว 200 คน ซึ่งซัพพอร์ตพนักงานประมาณ 5,000 คน บทความนี้คือบันทึกว่าเดือนแรกของ Tech Lead ผมทำอะไร อะไรได้ผล และอะไรที่ถ้าย้อนกลับไปได้ผมจะทำต่างออกไป

## สัปดาห์ที่ 1–2: Listening tour

สิ่งที่อยากทำที่สุดตอนเข้าไปใหม่คือเปิด code แล้วเริ่มแก้ แต่ผมบังคับตัวเองให้ฟังก่อนสองสัปดาห์ เพราะ Tech Lead คนใหม่ที่แก้ของก่อนเข้าใจบริบท มักจะทำลายความเชื่อใจของทีมเร็วกว่าที่คิด

ผมคุยตัวต่อตัวกับทุกคนในทีม และกับ user หลักของแต่ละระบบ คำถามที่ใช้ซ้ำทุกครั้งมีแค่นี้

- งานไหนที่คุณทำซ้ำทุกวันแล้วรู้สึกว่าเสียเวลา
- ครั้งล่าสุดที่ระบบพัง เกิดอะไรขึ้น และใครแก้
- ถ้าแก้ได้แค่อย่างเดียวในเดือนนี้ คุณจะแก้อะไร
- มีอะไรที่ "ห้ามแตะ" ไหม และเพราะอะไร

คำถามข้อสุดท้ายมีค่ามาก เพราะมันเผยให้เห็นจุดที่ทุกคนกลัว ซึ่งมักเป็นจุดที่ไม่มีเอกสารและมีคนรู้อยู่คนเดียว

ภาษาก็เป็นส่วนหนึ่งของ listening tour ด้วย ทีมและ user ใช้ทั้งอังกฤษ สเปน จีน และไทย ผมเรียนรู้เร็วว่าการพยายามพูดสเปนแม้จะไม่คล่อง ทำให้คนเปิดใจเล่าปัญหามากกว่าการคุยผ่านอังกฤษล้วน

## สัปดาห์ที่ 2–3: หา quick wins

หลังฟังครบ ผมเอาปัญหาทั้งหมดมาจัดเป็นสองแกน คือ ผลกระทบ กับ ความยาก แล้วเลือกเฉพาะอันที่ผลกระทบสูงแต่ทำได้ภายในไม่กี่วัน

Quick win ที่ดีมีลักษณะสามอย่าง

1. user มองเห็นผลทันที ไม่ใช่แค่ทีม dev
2. ไม่ต้องเปลี่ยน architecture
3. rollback ได้ง่ายถ้าพลาด

จุดประสงค์ของ quick wins ไม่ใช่แค่แก้ปัญหา แต่คือสร้างเครดิต เพื่อให้ตอนที่ต้องขอเปลี่ยนเรื่องใหญ่ในเดือนถัดไป คนจะยอมฟัง

## สัปดาห์ที่ 3–4: ตั้งกติกา deploy

ปัญหาที่ใหญ่ที่สุดที่ผมเจอจาก listening tour คือ deploy ไม่มีกติกากลาง ใครพร้อมก็ deploy ไม่มีบันทึกว่าอะไรขึ้นไปเมื่อไร พอมีปัญหาก็ไม่รู้ว่าต้อง rollback อะไร

ผมไม่ได้ออกกฎยาวเป็นหน้า แต่เริ่มจากสามอย่างที่เล็กที่สุดที่ได้ผล

- **Deploy list**: ทุก deploy ต้องมีรายการว่าระบบไหน, branch ไหน, เปลี่ยนอะไร, rollback ยังไง, ใครเป็นคนกด
- **Branch-merge policy**: merge เข้า main ผ่าน review เท่านั้น ห้าม push ตรง
- **Rollback owner**: ทุก deploy มีคนรับผิดชอบ rollback ชัดเจน และผมรับเองเป็นคนแรก

ตัวอย่าง deploy list ที่ทีมใช้

```markdown
## Deploy 2026-03-27

| System   | Branch          | Change                     | Rollback                  | Owner |
|----------|-----------------|----------------------------|---------------------------|-------|
| orders   | release/0327    | Fix export timeout         | Revert to tag v1.8.2      | Lead  |
| users    | release/0327    | Add language field         | Run down migration 0412   | Dev A |

- Pre-check: backup DB, notify users in channel
- Post-check: smoke test login + main report
```

สิ่งที่ทำให้กติกานี้ติดคือผมเป็นคนทำตามก่อน และไม่เคยข้ามแม้ตอนรีบ หลังจากนั้นเรื่องนี้พัฒนาต่อเป็นวิธีคิดที่ผมเขียนไว้ใน [เปลี่ยนทุก deploy ให้เป็น runbook](/blog/turn-every-deploy-into-runbook)

## สิ่งที่ผมจะทำต่างออกไป

**เขียน system map ตั้งแต่สัปดาห์แรก** ผมจดโน้ตจาก listening tour กระจัดกระจาย กว่าจะรวมเป็นภาพเดียวก็ปลายเดือน ถ้าเริ่มวาดตั้งแต่วันแรกแล้วเติมทีละนิด จะเห็นช่องโหว่เร็วกว่านี้

**ตั้งกติกา deploy เร็วกว่านี้หนึ่งสัปดาห์** ผมรอให้ "เข้าใจครบ" ก่อน แต่กติกาพื้นฐานอย่าง deploy list ไม่ต้องรอเข้าใจครบก็ทำได้ และมันช่วยให้เข้าใจระบบเร็วขึ้นด้วย

**มอบงานให้ทีมเร็วขึ้น** ช่วงแรกผมทำ quick wins เองหลายอัน เพราะเร็วกว่า แต่ผลคือทีมไม่ได้รู้สึกเป็นเจ้าของ ถ้าย้อนได้ ผมจะ pair กับคนในทีมแล้วให้เขาเป็นคนกด deploy

**ถามเรื่อง security ตั้งแต่แรก** ผมโฟกัสเรื่อง deploy กับ feature จนเรื่อง access control และ secret management ถูกเลื่อนออกไป ซึ่งภายหลังกลายเป็นงานใหญ่ ถ้าใส่คำถามเรื่องนี้ไว้ใน listening tour ตั้งแต่ต้นจะดีกว่า

## สรุป

เดือนแรกของ Tech Lead ไม่ใช่เวลาพิสูจน์ว่าเราเก่ง แต่เป็นเวลาเข้าใจว่าทีมเจ็บตรงไหน ฟังให้ครบ เลือก quick wins ที่ user เห็น ตั้งกติกา deploy ที่เล็กที่สุดที่ได้ผล แล้วทำตามมันเองก่อนทุกคน ส่วนสิ่งที่ผมพลาด คือรอนานเกินไปในเรื่องที่ไม่จำเป็นต้องรอ
