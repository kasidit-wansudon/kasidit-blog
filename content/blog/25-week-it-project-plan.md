ตอนรับตำแหน่ง Technical Lead ที่ OPPO Mexico ผมต้องทำ IT project plan ยาว 25 สัปดาห์ให้ผู้บริหารดู สิ่งที่ผมเรียนรู้คือแผนที่ดีไม่ใช่แผนที่ละเอียดที่สุด แต่คือแผนที่ทุกคนอ่านแล้วรู้ว่า "ตอนนี้เราอยู่เฟสไหน และจบเฟสนี้แล้วได้อะไร" บทความนี้จะแชร์โครงสร้างที่ผมใช้ พร้อม template ที่เอาไปปรับใช้ได้ทันที

## ทำไมต้องแบ่งเป็นเฟส ไม่ใช่ list ของงาน

ทีม IT ภายในองค์กรมักโดนงานสองแบบชนกันตลอด คืองาน support รายวัน (ระบบล่ม, user ขอแก้ข้อมูล, deploy hotfix) กับงาน project ระยะยาว ถ้าเขียนแผนเป็น list ของ feature อย่างเดียว พอสัปดาห์ที่สามโดน incident สองวัน แผนทั้งหมดก็เลื่อน และไม่มีใครรู้ว่าเลื่อนเพราะอะไร

การแบ่งเป็นเฟสช่วยสามอย่าง

- ผู้บริหารเห็นภาพรวมในหน้าเดียว
- แต่ละเฟสมี deliverable ชัด วัดได้ว่าจบหรือยัง
- งาน support ถูกนับเป็นงานจริงในแผน ไม่ใช่ "งานแทรก" ที่มองไม่เห็น

## โครงสร้าง IT project plan 25 สัปดาห์

ผมแบ่งเป็น 7 เฟส บางเฟสทับซ้อนกันได้ เพราะในชีวิตจริงงานไม่ได้เรียงเป็นเส้นตรง

### 1. Assessment (สัปดาห์ 1–3)

เป้าหมายคือ "รู้ว่ามีอะไรอยู่บ้าง" ก่อนจะแก้อะไร งานหลักคือ

- ทำ inventory ระบบทั้งหมด: ใครใช้, stack อะไร, deploy ยังไง, ใครเป็นเจ้าของ
- คุยกับ user หลักของแต่ละระบบ ถามว่าอะไรเจ็บที่สุด
- ดู risk ด้าน security และ backup เบื้องต้น

Deliverable คือ system map และ risk list ที่จัดลำดับแล้ว ห้ามข้ามเฟสนี้ เพราะถ้าข้าม เราจะไปแก้สิ่งที่ดังที่สุด ไม่ใช่สิ่งที่สำคัญที่สุด

### 2. Core Support (สัปดาห์ 2–25)

เฟสนี้ยาวตลอดโปรเจกต์ และผมจงใจใส่ไว้ในแผนตั้งแต่แรก มันคือการรักษาระบบเดิมให้เดินได้ ได้แก่ deploy, rollback, แก้ bug, ตอบ ticket ผมกำหนดสัดส่วนเวลาทีมไว้ชัดว่า support กินกี่เปอร์เซ็นต์ของสัปดาห์ เพื่อให้คำนวณ capacity ของงาน project ได้จริง

### 3. Project Management Setup (สัปดาห์ 3–5)

ก่อนลงมือสร้างอะไรใหม่ ต้องมีกติกากลางก่อน

- ระบบ ticket สำหรับรับ requirement
- branch-merge policy และ deploy-list template
- ประชุมสั้นประจำสัปดาห์ และรูปแบบ status report

ส่วนนี้ผมเขียนแยกไว้ใน [ทำระบบ ticketing ใน 2 วัน](/blog/ticketing-system-in-2-days)

### 4. Module Delivery (สัปดาห์ 5–18)

นี่คือเนื้อหลัก งานพัฒนาแต่ละ module ถูกแบ่งเป็นรอบละ 2–3 สัปดาห์ แต่ละรอบต้องจบด้วย demo ให้ user จริงดู ไม่ใช่แค่ "code เสร็จ" ผมเรียงลำดับ module ตาม risk list จากเฟส Assessment ไม่ใช่ตามความอยากของใคร

### 5. Capability Building (สัปดาห์ 10–20)

ทีมต้องเก่งขึ้นระหว่างทาง ไม่งั้นพอจบโปรเจกต์ทุกอย่างจะกลับไปพึ่งคนคนเดียว งานในเฟสนี้เช่น pair programming, code review ที่มี checklist, ให้คนในทีมเป็นคน deploy เองโดยมีผมคอยดู

### 6. Knowledge Transfer (สัปดาห์ 19–23)

เขียน runbook, system map ฉบับอัปเดต, owner list และให้คนรับช่วงลองทำงานจริงโดยที่เราไม่ช่วย เฟสนี้มักถูกบีบเวลา จึงต้องจองไว้ในแผนตั้งแต่วันแรก

### 7. Handover (สัปดาห์ 24–25)

ส่งมอบอย่างเป็นทางการ มี checklist ที่ทั้งสองฝ่ายเซ็นรับ และมีช่วง hypercare สั้น ๆ ที่ยังตอบคำถามได้

## Template ตารางแผน 25 สัปดาห์

นี่คือ template ที่ผมใช้เป็นหน้าแรกของเอกสาร

```markdown
| Phase                | Weeks  | Goal                         | Deliverable                       | Exit criteria                        |
|----------------------|--------|------------------------------|-----------------------------------|--------------------------------------|
| Assessment           | 1-3    | รู้สภาพระบบปัจจุบัน              | System map, risk list             | ผู้บริหาร review risk list แล้ว         |
| Core Support         | 2-25   | ระบบเดิมเดินได้ต่อเนื่อง            | Deploy log, ticket stats          | ไม่มี incident ค้างเกิน SLA            |
| PM Setup             | 3-5    | มีกติกาทำงานร่วมกัน              | Ticket system, deploy policy      | ทีมใช้จริงครบ 2 สัปดาห์                |
| Module Delivery      | 5-18   | ส่งมอบ module ตามลำดับ risk     | Demo + production release         | User sign-off ทุก module               |
| Capability Building  | 10-20  | ทีมทำงานได้เองไม่พึ่งคนเดียว      | Review checklist, pairing log     | คนในทีม deploy เองได้                 |
| Knowledge Transfer   | 19-23  | ความรู้อยู่ในเอกสาร ไม่อยู่ในหัว    | Runbooks, owner list              | ผู้รับช่วงทำ task จริงโดยไม่มีคนช่วย     |
| Handover             | 24-25  | ส่งมอบเป็นทางการ                | Handover checklist                | ทั้งสองฝ่ายเซ็นรับ                     |
```

คอลัมน์ที่สำคัญที่สุดคือ Exit criteria เพราะมันบังคับให้เราตอบว่า "จบ" แปลว่าอะไร ถ้าเขียนไม่ได้ แปลว่าเฟสนั้นยังไม่ชัด

## บทเรียนจากการใช้แผนนี้จริง

**เฟสทับซ้อนเป็นเรื่องปกติ** อย่าพยายามทำให้ Gantt chart สวย ให้ทำให้มันจริง Core Support ทับทุกเฟสเพราะมันทับจริง

**รายงานเป็นเฟส ไม่ใช่เป็นเปอร์เซ็นต์** การบอกว่า "เสร็จ 63%" ไม่มีความหมายกับผู้บริหาร แต่ "Module Delivery รอบ 3 จาก 5, demo วันศุกร์" เข้าใจทันที

**เลื่อนได้ แต่ต้องบอกเหตุผล** เมื่อ incident กินเวลา ผมบันทึกลงใน Core Support log แล้วอ้างอิงตอนอธิบายว่าทำไม Module Delivery เลื่อน ผู้บริหารยอมรับการเลื่อนที่มีหลักฐานได้ง่ายกว่าที่คิด

**Knowledge Transfer ต้องเริ่มก่อนที่คิด** ถ้ารอสัปดาห์สุดท้ายค่อยเขียนเอกสาร จะได้เอกสารที่ไม่มีใครอ่าน ให้เขียน runbook ทุกครั้งที่ deploy หรือแก้ปัญหา แล้วเฟส Knowledge Transfer จะเป็นแค่การรวบรวมและทดสอบ

## สรุป

IT project plan ที่ใช้ได้จริงคือแผนที่ยอมรับว่างาน support มีอยู่ แบ่งงานเป็นเฟสที่มี deliverable และ exit criteria ชัด และจองเวลาไว้ให้ทีมเก่งขึ้นและส่งต่อความรู้ ลองเอา template ด้านบนไปใส่ระบบของคุณ เริ่มจากเติมคอลัมน์ Exit criteria ให้ครบก่อน แล้วจะเห็นทันทีว่าเฟสไหนยังคิดไม่จบ
