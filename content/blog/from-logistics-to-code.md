ก่อนจะเขียนโค้ดเป็นอาชีพ ผมทำงานด้านโลจิสติกส์และงานก่อสร้าง หลายคนคิดว่าการย้ายจากงานใช้แรงมาเป็น developer คือการเริ่มต้นใหม่จากศูนย์ แต่ยิ่งทำงานซอฟต์แวร์นานขึ้น ผมยิ่งพบว่าสิ่งที่งานใช้แรงสอนไว้ยังใช้ได้ทุกวัน โดยเฉพาะเรื่องการทำงานภายใต้แรงกดดัน โพสต์นี้คือบทเรียนจากโลจิสติกส์และการก่อสร้างที่ผมพกติดตัวมาในการเขียนโค้ด

## งานโลจิสติกส์สอนเรื่อง flow

งานโลจิสติกส์คือการทำให้ของเคลื่อนจากจุดหนึ่งไปอีกจุดหนึ่งให้ถูกต้อง ครบ และตรงเวลา สิ่งที่เห็นชัดที่สุดคือ งานไม่ได้ช้าเพราะทุกจุดช้า แต่ช้าเพราะมีคอขวดจุดเดียว รถมาครบแต่ที่ขึ้นของมีช่องเดียว ทุกคันก็ต้องรอ

ในซอฟต์แวร์ก็เหมือนกัน ระบบช้าเพราะ query ตัวเดียว ทีมช้าเพราะต้องรอ review จากคนคนเดียว การแก้ที่ได้ผลจึงเริ่มจากการหาคอขวด ไม่ใช่การเร่งทุกอย่างพร้อมกัน

### นับของทุกครั้งที่ส่งต่อ

ในคลังสินค้า การนับของทุกครั้งที่มีการส่งต่อเป็นเรื่องปกติ ถ้าไม่นับ เมื่อของหายจะไม่มีทางรู้ว่าหายที่จุดไหน

สิ่งนี้คือที่มาของนิสัยที่ผมใส่ใจเรื่อง log และการตรวจข้อมูลในทุกจุดที่ข้อมูลข้ามระบบ เช่น ตอนรับ webhook ตอนนำเข้าไฟล์ หรือตอน sync ระหว่าง database ถ้าตัวเลขต้นทางกับปลายทางไม่ตรงกัน เราต้องรู้ได้ว่าหายระหว่างทางตรงไหน

```text
checklist ทุกจุดส่งต่อข้อมูล
- นับจำนวนก่อนส่ง และหลังรับ
- บันทึกเวลา ต้นทาง ปลายทาง
- ถ้าไม่ตรง ให้หยุดและแจ้ง อย่าข้ามไปเงียบ ๆ
```

## งานก่อสร้างสอนเรื่องแบบแปลนและความปลอดภัย

ในงานก่อสร้าง ไม่มีใครเทปูนก่อนดูแบบ และไม่มีใครขึ้นที่สูงโดยไม่มีอุปกรณ์ป้องกัน ความผิดพลาดบางอย่างแก้ไม่ได้ เทผิดที่ต้องทุบทิ้ง และอุบัติเหตุบางอย่างไม่มีโอกาสแก้ตัว

### ออกแบบก่อนสร้าง

นิสัยนี้ทำให้ผมไม่ชอบเริ่มเขียนโค้ดโดยไม่รู้ว่าจะเปลี่ยนไฟล์ไหน ข้อมูลไหลอย่างไร และอะไรที่ต้องไม่แตะ ไม่จำเป็นต้องเขียนเอกสารยาว บางครั้งแค่โน้ตห้าบรรทัดก็พอ แต่ต้องมีก่อนลงมือ

### บางอย่างย้อนกลับไม่ได้

ในซอฟต์แวร์ เรามักคิดว่าทุกอย่าง undo ได้ แต่ไม่จริงเสมอไป การลบข้อมูลบน production การรัน migration ที่ drop คอลัมน์ หรือการส่งข้อความหาลูกค้าจำนวนมาก ล้วนย้อนกลับไม่ได้ งานก่อสร้างสอนผมให้หยุดคิดหนึ่งจังหวะก่อนทำสิ่งที่ย้อนไม่ได้ และถามตัวเองว่ามีแผนสำรองหรือยัง

## แรงกดดันในงานใช้แรง กับแรงกดดันในงานซอฟต์แวร์

แรงกดดันในงานใช้แรงจับต้องได้: รถรอส่งของ คนงานรอวัสดุ ฝนกำลังจะตก ทุกคนเห็นปัญหาตรงหน้า และต้องตัดสินใจเร็ว

แรงกดดันในงานซอฟต์แวร์มองไม่เห็นแต่หนักไม่แพ้กัน: ระบบล่มตอนกลางคืน ผู้ใช้แจ้งว่าตัวเลขผิด deadline ใกล้เข้ามา สิ่งที่ผมพบคือหลักการรับมือเหมือนกันมาก

1. **หยุดหายใจก่อน** การรีบทำโดยไม่คิดทำให้ปัญหาใหญ่ขึ้นเกือบทุกครั้ง
2. **ทำให้ปลอดภัยก่อนแก้** ในไซต์งานคือกั้นพื้นที่ ในซอฟต์แวร์คือ rollback หรือปิดฟีเจอร์ที่มีปัญหา
3. **สื่อสารสั้นและชัด** บอกว่าเกิดอะไร กำลังทำอะไร และจะอัปเดตอีกเมื่อไร
4. **หาสาเหตุทีหลัง** เมื่อสถานการณ์นิ่งแล้วค่อยวิเคราะห์ ไม่ใช่ระหว่างที่ทุกอย่างยังพัง

## ทำงานกับคนที่หลากหลาย

ทั้งงานโลจิสติกส์และก่อสร้างทำให้ผมได้ทำงานกับคนที่ต่างกันมาก ทั้งพื้นเพ อายุ และวิธีคิด สิ่งที่ได้เรียนรู้คือ คำสั่งที่ชัดเจนและให้เกียรติกัน ได้ผลกว่าคำสั่งที่ยาวหรือดุดัน เวลาอธิบายงานให้ใครสักคน ผมพยายามบอกว่า "ทำอะไร" และ "ทำไม" ไม่ใช่แค่ "ทำอะไร"

## ความอดทนกับงานซ้ำ ๆ

งานใช้แรงมีความซ้ำซากเป็นส่วนใหญ่ ยกของเดิม ตรวจของเดิม ทุกวัน การเขียนโค้ดก็มีส่วนแบบนี้ไม่น้อย ทั้งการไล่ bug การเขียน test และการแก้ข้อมูล ความอดทนกับงานซ้ำทำให้ผมไม่ข้ามขั้นตอนที่น่าเบื่อแต่จำเป็น และเมื่อเจองานซ้ำมากพอ ผมก็รู้ว่าถึงเวลาเขียนสคริปต์หรือทำเครื่องมือมาช่วยแล้ว

## สำหรับคนที่กำลังจะเปลี่ยนสายงาน

ถ้าคุณมาจากงานที่ไม่ใช่ IT อย่ามองว่าประสบการณ์เดิมไม่มีค่า ทักษะอย่างการวางแผน การทำงานกับคน การรับมือแรงกดดัน และความรับผิดชอบต่องานที่ส่งมอบ คือสิ่งที่หลายทีมต้องการ และสอนกันได้ยากกว่าภาษาโปรแกรม งานแรกที่ได้เงินจากการเขียนโค้ดของผมเป็นอย่างไร ผมเล่าไว้ในโพสต์ถัดไป หรือถ้าอยากรู้ว่าทำไมผมเริ่มเขียนบล็อกนี้ อ่านได้ที่ [ทำไมผมเริ่มเขียนบล็อก](/blog/why-i-write-this-blog)

## สรุป

งานโลจิสติกส์สอนผมให้มองหาคอขวดและนับของทุกจุดส่งต่อ งานก่อสร้างสอนให้ออกแบบก่อนสร้างและเคารพสิ่งที่ย้อนกลับไม่ได้ ทั้งสองงานสอนวิธีรับมือแรงกดดัน: หยุดคิด ทำให้ปลอดภัย สื่อสารชัด แล้วค่อยหาสาเหตุ บทเรียนเหล่านี้ยังอยู่ในทุกการ deploy และทุกการแก้ปัญหาของผมทุกวันนี้
