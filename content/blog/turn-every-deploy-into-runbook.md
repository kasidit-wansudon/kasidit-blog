ทุกครั้งที่ deploy เสร็จหรือแก้ปัญหา production ได้ ผมจะถามตัวเองหนึ่งคำถาม: "ถ้าพรุ่งนี้ต้องทำแบบนี้อีก แต่ผมไม่อยู่ คนในทีมจะทำได้ไหม" ถ้าคำตอบคือไม่ แปลว่างานยังไม่จบ สิ่งที่ขาดคือ **runbook** และในโพสต์นี้ผมจะแชร์วิธีเปลี่ยนทุก deploy ให้เป็น runbook ที่ใช้ซ้ำได้ ซึ่งเป็นนิสัยที่ช่วยทีมเล็กของผมมากที่สุดนิสัยหนึ่ง

## ทำไมทีมเล็กต้องมี runbook มากกว่าทีมใหญ่

ตอนเป็น Technical Lead ที่ OPPO Mexico ผมดูแลทีม 5 คน ที่ต้องรับผิดชอบระบบภายในมากกว่า 6 ระบบ และต้องเป็นเจ้าของ deploy และ rollback รายวัน ในทีมขนาดนี้ ความรู้มักไปกองอยู่ที่คนหนึ่งหรือสองคน พอคนนั้นลาป่วย ติดประชุม หรือย้ายงาน ทุกอย่างช้าลงทันที

ทีมใหญ่มีคนสำรองและมีทีม platform แยก ทีมเล็กไม่มี runbook จึงเป็นเหมือน "คนสำรอง" ที่ราคาถูกที่สุด

ประโยชน์ที่ผมเห็นชัด:

- คนใหม่ทำ deploy ครั้งแรกได้โดยไม่ต้องนั่งข้างคนเก่า
- rollback เร็วขึ้น เพราะขั้นตอนถอยกลับเขียนไว้ก่อนแล้ว ไม่ต้องคิดตอนตื่นเต้น
- ปัญหาเดิมที่เกิดซ้ำ แก้ได้ในไม่กี่นาทีแทนที่จะไล่หาใหม่
- การส่งมอบงาน (handover) ง่ายขึ้นมาก เพราะเอกสารสะสมมาเรื่อย ๆ ไม่ต้องเขียนใหม่ทีเดียวตอนท้าย

## Template runbook ที่ผมใช้

ผมทดลองหลายรูปแบบ สุดท้ายเหลือ template ที่สั้นพอให้คนยอมเขียนจริง:

```markdown
# <ชื่องาน: เช่น Deploy ระบบ orders ขึ้น production>

## ใช้เมื่อไร
- เงื่อนไขที่ต้องทำ runbook นี้

## ก่อนเริ่ม (pre-check)
- [ ] branch / tag ที่จะ deploy
- [ ] backup database ล่าสุดเมื่อไร
- [ ] แจ้งผู้ใช้หรือทีมที่เกี่ยวข้องแล้ว

## ขั้นตอน
1. คำสั่งที่รันจริง (copy-paste ได้)
2. ผลลัพธ์ที่ควรเห็นในแต่ละขั้น

## ตรวจหลัง deploy (verify)
- URL / endpoint ที่ต้องเปิดดู
- log ที่ต้องเช็ก

## Rollback
1. ขั้นตอนถอยกลับ
2. จุดที่ถอยกลับไม่ได้ (เช่น migration ที่ลบคอลัมน์)

## ปัญหาที่เคยเจอ
- อาการ -> สาเหตุ -> วิธีแก้

## อัปเดตล่าสุด
- วันที่ / คนแก้ / เปลี่ยนอะไร
```

หัวข้อที่สำคัญที่สุดคือ **ผลลัพธ์ที่ควรเห็น** และ **ปัญหาที่เคยเจอ** สองส่วนนี้คือความรู้ที่อยู่ในหัวคน ซึ่งหายไปเร็วที่สุด

## สิ่งที่ต้องบันทึก (และสิ่งที่ไม่ควรบันทึก)

**ควรบันทึก**

- คำสั่งที่รันจริง ไม่ใช่คำอธิบายกว้าง ๆ เช่น เขียนว่า `php artisan migrate --force` ไม่ใช่ "รัน migration"
- ลำดับขั้น และเหตุผลถ้าลำดับนั้นสำคัญ
- สัญญาณว่าสำเร็จ เช่น status code, ข้อความใน log, หน้าจอที่ควรเห็น
- จุดที่ย้อนกลับไม่ได้ ต้องเตือนชัด ๆ
- เวลาโดยประมาณของแต่ละขั้น จะได้รู้ว่าอะไรผิดปกติ

**ไม่ควรบันทึก**

- password, API key, token ลงในเอกสาร ให้เขียนแค่ว่าเก็บไว้ที่ไหน เช่น secrets manager หรือ password manager ของทีม
- ข้อมูลที่เปลี่ยนบ่อยจนเอกสารล้าสมัยภายในสัปดาห์ ให้ลิงก์ไปยังแหล่งจริงแทน

## ทำให้เป็นนิสัย ไม่ใช่โปรเจกต์เอกสาร

ความผิดพลาดที่พบบ่อยคือการประกาศ "สัปดาห์เขียนเอกสาร" แล้วทุกคนเขียนสิ่งที่จำได้ ผลคือเอกสารที่ไม่ตรงกับความจริงตั้งแต่วันแรก

วิธีที่ได้ผลกับผมคือ:

1. **เขียนระหว่างทำ** เปิดไฟล์ runbook ไว้ข้าง terminal ตอน deploy แล้ว copy คำสั่งลงไปทันที
2. **ผูกกับ deploy list** ทุกรายการใน deploy list ของทีมต้องมีลิงก์ runbook ถ้าไม่มี ถือว่างานยังไม่ครบ
3. **คนถัดไปเป็นคนแก้** คนที่ใช้ runbook แล้วเจอขั้นที่ผิดหรือขาด ต้องแก้ทันที วิธีนี้ทำให้เอกสารดีขึ้นทุกครั้งที่ถูกใช้
4. **review สั้น ๆ** ให้คนที่ไม่เคยทำงานนั้นลองอ่าน ถ้าอ่านแล้วต้องถาม แปลว่ายังเขียนไม่พอ

## ไม่ใช่แค่ deploy: ทุกการแก้ปัญหาก็เป็น runbook ได้

หลายคนคิดว่า runbook มีไว้สำหรับ deploy เท่านั้น แต่ runbook ที่ผมใช้บ่อยที่สุดกลับเป็นเรื่องแก้ปัญหา เช่น "queue ค้าง ต้องทำอย่างไร" หรือ "ผู้ใช้ login ไม่ได้หลังเปลี่ยนรหัสผ่าน ตรวจอะไรก่อน" ปัญหาแบบนี้เกิดไม่บ่อย พอเกิดอีกครั้งทุกคนลืมไปแล้วว่าครั้งก่อนแก้อย่างไร

กฎของทีมผมคือ ถ้าปัญหาไหนใช้เวลาไล่หาเกินครึ่งชั่วโมง คนที่แก้ต้องเขียน runbook สั้น ๆ ไว้ แม้จะมีแค่สามบรรทัด: อาการ, สาเหตุ, คำสั่งที่ใช้แก้ เท่านี้ก็พอให้ครั้งหน้าเร็วขึ้นหลายเท่า และ helpdesk สามารถใช้ runbook เดียวกันตอบผู้ใช้ได้ทันทีโดยไม่ต้องรอโปรแกรมเมอร์

## ให้ AI ช่วยเก็บ runbook

ใน Kasidit ผมทำคำสั่ง `/kasi-acknowledge` ไว้สำหรับเรื่องนี้โดยตรง หลังจาก agent ช่วย deploy หรือแก้ปัญหาเสร็จ คำสั่งนี้จะสรุปขั้นตอนที่เพิ่งทำจริงออกมาเป็น runbook ตาม template แล้วเก็บไว้ในโฟลเดอร์ knowledge ของโปรเจกต์ ครั้งต่อไปค้นเจอได้ทันที

จุดสำคัญคือ runbook ต้องมาจาก "สิ่งที่ทำจริง" ไม่ใช่สิ่งที่ AI คิดว่าน่าจะทำ ผมจึงยังต้องอ่านทวนทุกครั้งก่อนเก็บ ส่วนการส่งต่อเอกสารให้ทีมใหม่ ผมเล่าไว้ใน [เอกสาร handover ที่ใช้งานได้จริง](/blog/handover-documentation-that-works)

## สรุป

runbook คือคนสำรองที่ถูกที่สุดของทีมเล็ก ใช้ template สั้น ๆ ที่มีคำสั่งจริง ผลลัพธ์ที่ควรเห็น ขั้นตอน rollback และปัญหาที่เคยเจอ เขียนระหว่างทำ ผูกกับ deploy list และให้คนที่ใช้เป็นคนแก้ ทำแบบนี้ไปไม่กี่เดือน ทีมจะพึ่งคนใดคนหนึ่งน้อยลงอย่างเห็นได้ชัด
