ผมใช้ AI เขียนโค้ดร่วมกันทุกวัน และยอมรับว่ามันทำให้ผมทำงานเร็วขึ้นจริง แต่ช่วงแรกผมก็เคยเสียเวลามากกว่าเดิม เพราะรับโค้ดก้อนใหญ่มาโดยไม่ได้อ่าน แล้วต้องมานั่งไล่ bug ที่ตัวเองไม่ได้เขียน หลังจากนั้นผมตั้งกฎ pair programming กับ AI ให้ตัวเองไม่กี่ข้อ และใช้มาตลอด โพสต์นี้คือกฎชุดนั้น

## มอง AI เป็นคู่ pair ไม่ใช่คนที่ทำแทน

การ pair programming แบบดั้งเดิมมีคนหนึ่งเป็น driver ที่พิมพ์ และอีกคนเป็น navigator ที่คิดภาพรวมและคอยตรวจ เมื่อทำงานกับ AI ผมให้ AI เป็น driver ที่พิมพ์เร็วมาก ส่วนผมต้องเป็น navigator เสมอ ถ้าผมเลิกทำหน้าที่ navigator เมื่อไร ก็ไม่ใช่ pair programming แล้ว แต่เป็นการโยนงานให้เครื่องแล้วภาวนา

## กฎข้อ 1: ขอ diff เล็ก

ผมไม่สั่ง "ทำระบบ export ทั้งหมดให้หน่อย" แต่จะแบ่งเป็นขั้น เช่น

1. เพิ่ม method ใน service ที่ดึงข้อมูลตามช่วงวันที่
2. เพิ่ม endpoint ที่เรียก method นั้น
3. เพิ่มการแปลงเป็น CSV
4. เพิ่มปุ่มบนหน้าจอ

ทุกขั้นต้องเล็กพอที่ผมอ่าน diff จบได้ในไม่กี่นาที เหตุผลง่ายมาก diff ยาวสามร้อยบรรทัดคนจะ "ดูผ่าน ๆ" แต่ diff ยาวสามสิบบรรทัดคนจะอ่านจริง และ bug ซ่อนตัวใน diff ใหญ่ได้ง่ายกว่าเสมอ

ข้อดีอีกอย่างคือถ้าขั้นไหนผิด ผมทิ้งแค่ขั้นนั้นแล้วเริ่มใหม่ได้ ไม่ต้องรื้อทั้งก้อน

## กฎข้อ 2: test มาก่อน

ก่อนให้ AI แก้ logic สำคัญ ผมให้มันเขียน test ที่อธิบายพฤติกรรมที่ต้องการก่อน แล้วผมอ่าน test นั้นว่าตรงกับที่ผมคิดไหม จากนั้นค่อยให้มันเขียนโค้ดให้ test ผ่าน

```php
public function test_export_only_includes_orders_in_date_range(): void
{
    Order::factory()->create(['created_at' => '2025-12-31']);
    $inRange = Order::factory()->create(['created_at' => '2026-01-10']);

    $rows = app(OrderExportService::class)
        ->rows('2026-01-01', '2026-01-31');

    $this->assertCount(1, $rows);
    $this->assertSame($inRange->id, $rows[0]['id']);
}
```

test แบบนี้อ่านง่ายกว่าโค้ดจริงมาก และเป็นสัญญาที่ชัดเจนระหว่างผมกับ AI ถ้า AI เข้าใจโจทย์ผิด ผมจะเห็นตั้งแต่ตอนอ่าน test ยังไม่ต้องรอให้มันเขียนโค้ดผิดไปทั้งก้อน

ข้อควรระวังคือ ต้องดูว่า AI ไม่ได้ "แก้ test ให้ผ่าน" แทนการแก้โค้ด ถ้าเห็น diff ไปแตะไฟล์ test หลังจากที่เราตกลงกันแล้ว ให้หยุดถามทันที

## กฎข้อ 3: ไม่รับโค้ดที่ยังไม่ได้ verify

คำว่า "เสร็จแล้ว" จาก AI ไม่ได้แปลว่าเสร็จ ผมนับว่าเสร็จก็ต่อเมื่อ

- test รันผ่านจริงบนเครื่อง ไม่ใช่ AI บอกว่า "ควรจะผ่าน"
- รันแอปแล้วลองกดใช้งาน flow นั้นเองอย่างน้อยหนึ่งรอบ
- ไม่มี error ใหม่ใน log

runtime คือผู้ตัดสิน ไม่ใช่ความมั่นใจของ AI และไม่ใช่ความรู้สึกของผม AI สามารถอธิบายโค้ดที่ผิดได้อย่างมั่นใจมาก จึงเชื่อคำอธิบายแทนผลการรันไม่ได้

## กฎข้อ 4: อ่านทุกบรรทัดก่อน commit

ข้อนี้ฟังดูน่าเบื่อแต่สำคัญที่สุด ถ้าผม commit โค้ดที่ไม่ได้อ่าน แปลว่าผมเอาชื่อตัวเองไปรับรองสิ่งที่ไม่รู้ว่ามันทำอะไร สิ่งที่ผมมองหาเวลาอ่าน:

- ชื่อตัวแปร ฟังก์ชัน หรือ method ที่ไม่มีอยู่จริงใน codebase
- การแก้ไฟล์ที่ไม่ได้ขอ
- การกลืน exception เงียบ ๆ ด้วย `try/catch` ว่างเปล่า
- query ที่อาจทำให้เกิด N+1 หรือดึงข้อมูลเกินจำเป็น
- ค่าที่ hardcode ไว้ เช่น URL หรือ credential

ถ้าอ่านแล้วไม่เข้าใจบรรทัดไหน ผมถาม AI ให้อธิบาย ถ้ายังไม่เข้าใจ ผมเขียนใหม่ให้เรียบง่ายกว่าเดิม โค้ดที่ทีมไม่เข้าใจคือหนี้ที่จะกลับมาเก็บดอกเบี้ยตอนดึก

## กฎข้อ 5: บอก scope ให้ชัด และบอกสิ่งที่ห้ามแตะ

prompt ที่ดีของผมมักมีสามส่วน: ปัญหาคืออะไร ไฟล์ไหนเกี่ยว และอะไรที่ไม่ต้องแก้ เช่น "แก้แค่ `OrderExportService` ไม่ต้อง refactor controller และไม่ต้องเปลี่ยน format วันที่" ประโยคสุดท้ายนี้ช่วยกัน AI จาก "ความหวังดี" ที่แก้เกินไปได้มาก

## เมื่อไรควรหยุดใช้ AI ชั่วคราว

ถ้า AI แก้ bug เดิมวนไปวนมาเกินสองรอบ ผมหยุดแล้วกลับมาอ่านโค้ดเองพร้อม log จริง เรื่องนี้ผมเขียนไว้ละเอียดใน [AI hallucination และ ghost bug](/blog/ai-hallucination-ghost-bugs) สั้น ๆ คือ ถ้าเครื่องมือเริ่มเดา เราต้องกลับมาเป็นคนที่ถือหลักฐาน

## สรุป

กฎ pair programming กับ AI ของผมมีห้าข้อ: ขอ diff เล็ก, เขียน test ก่อน, ไม่รับโค้ดที่ยังไม่ได้ verify ด้วยการรันจริง, อ่านทุกบรรทัดก่อน commit และบอก scope รวมถึงสิ่งที่ห้ามแตะให้ชัด AI ทำให้เราพิมพ์เร็วขึ้น แต่ความรับผิดชอบต่อโค้ดยังเป็นของเราเต็มร้อย
