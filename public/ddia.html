Part 1 Foundations of Data Systems

Reliability, Scalability, Maintainability Ch.1

3 เป้าหมายหลักของระบบ data-intensive — เลือกไม่ได้แค่อันเดียว

🛡 Reliability

ทำงานถูกต้องแม้มี fault — hardware พัง, bug, user ป้อนข้อมูลผิด

📈 Scalability

รับ load ที่เพิ่มขึ้นได้ — วัดด้วย throughput, latency percentile (p99)

🔧 Maintainability

คนอื่นทำงานต่อได้ง่าย — operability, simplicity, evolvability

⚖️ Fault vs Failure

Fault = ส่วนหนึ่งผิดปกติ, Failure = ระบบล้มทั้งหมด ออกแบบให้ tolerate fault

Twitter fanout problem — ส่ง tweet ให้ follower ล้านคน: push vs pull trade-off

Data Models Ch.2

วิธีที่เราแทนข้อมูล — กำหนดว่าจะทำอะไรได้บ้าง

Modelเหมาะกับตัวอย่าง
Relational (SQL)ข้อมูล structured, มี relationship ซับซ้อน, ACID ต้องการMySQL, PostgreSQL
Document (NoSQL)ข้อมูล self-contained, schema flexible, read ทีเดียวครบMongoDB, DynamoDB
Graphความสัมพันธ์ซับซ้อนมาก เช่น social network, fraud detectionNeo4j
ไม่มี model ที่ดีที่สุด — ดู access pattern ก่อนเลือก DB

Storage & Retrieval — Index คืออะไร Ch.3

DB เก็บข้อมูลอย่างไร และหาข้อมูลได้เร็วแค่ไหน

🌳 B-Tree Index

Standard ใน SQL DB — ดีสำหรับ read-heavy, range query ได้

📝 LSM-Tree + SSTable

ใน LevelDB, RocksDB, Cassandra — ดีสำหรับ write-heavy, append-only

OLTP vs OLAP: OLTP = transaction รายวัน (low latency, high volume) | OLAP = analytics query ข้อมูลเยอะ (data warehouse, Redshift, BigQuery)
Column-oriented storage (Parquet, ORC) — query analytics เร็วขึ้น 10-100x เพราะอ่านแค่ column ที่ต้องการ

Part 2 Distributed Data

Replication — ก๊อปข้อมูลไว้หลายที่ Ch.5

เหตุผลหลัก: latency ต่ำ (ใกล้ user) + high availability + scale read

👑 Single-Leader

มี leader รับ write, follower รับ read — ง่าย, consistent แต่ leader เป็น bottleneck

👑👑 Multi-Leader

หลาย DC เขียนได้พร้อมกัน — latency ต่ำข้ามประเทศ แต่ conflict ยาก

🤝 Leaderless

Dynamo-style — quorum write/read, ไม่มี single point of failure

⏱ Replication Lag

Async replication = follower อาจข้อมูลเก่า — "read-your-writes" consistency ต้องจัดการพิเศษ

Replication lag ทำให้ user เห็นข้อมูลเก่าหลัง write — อย่า assume follower = up-to-date เสมอ

Partitioning / Sharding Ch.6

แบ่งข้อมูลออกเป็นก้อน เก็บแยก node — scale เกินกว่า 1 machine ได้

🔑 By Key Range

เรียงตาม key — range query ง่าย แต่ hotspot ถ้า key ไม่กระจาย

#️⃣ By Hash

Hash key → กระจาย load ดี แต่ range query ช้า

Hotspot problem: ถ้า partition key เดิมถูกเข้าถึงเยอะ (เช่น celebrity account) — ต้องเพิ่ม random suffix หรือ application-level spreading
Cassandra ใช้ consistent hashing, DynamoDB ใช้ partition key + sort key

Transactions & ACID Ch.7

การ์ด IT ที่ต้องรู้ก่อนใช้ database ใดก็ตาม

⚛️ Atomicity

ทำทั้งหมดหรือไม่ทำเลย — ไม่มีครึ่งๆ กลางๆ

🔒 Isolation

Transaction ไม่เห็นกันระหว่างทำ — Serializable, Snapshot, Read Committed

💾 Durability

Commit แล้วไม่หาย แม้ crash — write-ahead log (WAL)

🎭 Isolation Levels

Read Uncommitted → Read Committed → Repeatable Read → Serializable (เร็ว↕ช้า)

Phantom read / dirty read / lost update — ปัญหาที่เกิดเมื่อ isolation level ต่ำเกินไป ต้องรู้ว่า DB ที่ใช้อยู่รองรับระดับไหน
MySQL InnoDB default = Repeatable Read | PostgreSQL default = Read Committed

ปัญหาของ Distributed Systems Ch.8

ทำไม distributed system ถึงยากกว่าที่คิด

🌐 Network

Packet หาย, ช้า, duplicate ได้เสมอ — timeout ≠ failure

⏰ Clocks

NTP drift — อย่า trust timestamp ข้าม node สำหรับ ordering

🧟 Process Pause

GC pause, VM suspension — node อาจ "หายไป" แล้วกลับมา ข้อมูล stale

🔮 No global state

ไม่มีใครเห็น "ปัจจุบัน" เหมือนกัน — ทุกอย่างคือ approximation

อย่า assume network reliable, อย่า assume clock sync — design for failure, not against it

Consistency & Consensus Ch.9

CAP Theorem และ consensus protocol — หัวใจของ distributed DB

📐 CAP Theorem

เลือกได้แค่ 2 จาก 3: Consistency, Availability, Partition tolerance — ในความเป็นจริง P หลีกเลี่ยงไม่ได้ → เลือก CP หรือ AP

🗳 Consensus

Paxos / Raft — ทำให้ nodes ตกลงกันได้แม้มีบางตัวล้ม ใช้ใน etcd, ZooKeeper, CockroachDB

Linearizability = ทุก read เห็นข้อมูลล่าสุด เหมือนมี copy เดียว — แพงมาก (latency สูง)

Eventual Consistency = ข้อมูลจะตรงกันในที่สุด แต่ไม่รู้เมื่อไหร่ — เร็วกว่า ถูกกว่า
DynamoDB, Cassandra = eventual consistency by default | Google Spanner = external consistency (linearizable แบบ global)
Part 3 Derived Data

Batch Processing Ch.10

ประมวลผลข้อมูลปริมาณมากในครั้งเดียว — offline, ไม่ต้องการ real-time

MapReduce philosophy: เอา code ไปหาข้อมูล (แทนที่จะดึงข้อมูลมา) — sort-merge join, distributed grep

Modern alternatives: Spark, Flink — in-memory, DAG execution แทน disk-heavy MapReduce
Batch = bounded dataset (ข้อมูลมีจุดสิ้นสุด) — ต่างจาก stream ที่ไม่มีจุดจบ

Stream Processing Ch.11

ประมวลผลข้อมูลแบบ real-time ขณะที่มันไหลเข้ามา

📨 Message Queue

RabbitMQ — deliver แล้วลบ, low latency, ไม่เก็บประวัติ

📜 Log-based (Kafka)

เก็บ event ทุกอย่าง, consumer อ่านซ้ำได้, replay ได้ — เหมาะ audit, reprocessing

Event sourcing: เก็บทุก event แทนที่จะเก็บ current state — ย้อน state ณ เวลาใดก็ได้

CQRS: แยก read model กับ write model — write = event store, read = materialized view
Kafka ที่ OPPO/Alibaba ecosystem ใช้กันมาก — DingTalk notification, order processing, HR sync events

The Future of Data Systems Ch.12

บทสรุปและ philosophy ของ Kleppmann

Lambda Architecture: batch layer (accurate) + speed layer (real-time) → merge ผล

Kappa Architecture: stream เดียวจัดการทุกอย่าง — replay batch ด้วย Kafka

Dataflow thinking: ระบบที่ดีคือ pipeline ของ transformation — input → transform → output ชัดเจน ไม่มี side effect ซ่อน
เลือก tool ตาม access pattern ไม่ใช่ตาม hype — "use the right tool for the job"
