งานส่วนใหญ่ที่ผมทำในฐานะ full-stack developer คือระบบภายในที่ใช้กับการดำเนินงานหลายประเทศ ข้อมูลโตทุกวัน และหน้าจอที่เคยเปิดเร็วเมื่อปีก่อนก็เริ่มช้าลงโดยไม่มีใครแก้โค้ดเลย MySQL query optimization จึงกลายเป็นงานที่ผมกลับมาทำซ้ำเป็นระยะ ล่าสุดผมลด latency ของ query หลักกลุ่มหนึ่งได้กว่า 40% โดยไม่ได้เพิ่ม server แม้แต่ตัวเดียว โพสต์นี้คือขั้นตอนที่ผมใช้ เรียงตามลำดับที่ผมทำจริง

## 1. วัดก่อน อย่าเดา

ก่อนแตะ index ผมเปิด slow query log และจดรายการ query ที่ช้าที่สุดพร้อมความถี่ที่ถูกเรียก query ที่ใช้เวลา 2 วินาทีแต่ถูกเรียกวันละครั้ง สำคัญน้อยกว่า query ที่ใช้ 200 ms แต่ถูกเรียกทุกครั้งที่ผู้ใช้เปิด dashboard

สิ่งที่ผมจดสำหรับแต่ละ query:

- เวลาเฉลี่ยและเวลาที่แย่ที่สุด
- จำนวนครั้งที่ถูกเรียกต่อวัน
- หน้าจอหรือ API ไหนเป็นคนเรียก

ตัวเลขชุดนี้คือ baseline ถ้าไม่มี baseline เราจะไม่มีทางรู้ว่าที่แก้ไปนั้นดีขึ้นจริงหรือแค่รู้สึกว่าเร็วขึ้น

## 2. อ่าน EXPLAIN ให้เป็น

`EXPLAIN` คือเครื่องมือที่คุ้มที่สุดในการทำ MySQL query optimization ช่องที่ผมดูเป็นอันดับแรกมีสี่ช่อง

- `type` ถ้าเห็น `ALL` แปลว่า full table scan ซึ่งมักเป็นต้นเหตุ
- `key` index ที่ MySQL เลือกใช้จริง (ไม่ใช่ที่เราคิดว่ามันจะใช้)
- `rows` จำนวนแถวที่คาดว่าต้องอ่าน ยิ่งน้อยยิ่งดี
- `Extra` ถ้าเห็น `Using filesort` หรือ `Using temporary` ให้ระวัง

ตัวอย่าง query ที่พบบ่อย คือหน้ารายการ order ที่กรองตามสถานะและช่วงวันที่ แล้วเรียงตามวันที่ล่าสุด

```sql
EXPLAIN
SELECT id, customer_id, total, created_at
FROM orders
WHERE status = 'paid'
  AND created_at >= '2026-01-01'
ORDER BY created_at DESC
LIMIT 50;
```

ถ้าตารางมีแค่ index เดี่ยวบน `status` ผลที่ได้มักเป็นการอ่านทุกแถวที่ `status = 'paid'` แล้วค่อยเรียงใน memory ซึ่งช้าลงเรื่อย ๆ ตามจำนวน order

## 3. Composite index ต้องเรียงคอลัมน์ให้ถูก

กฎที่ผมใช้คือ คอลัมน์ที่เทียบแบบเท่ากับ (`=`) มาก่อน ตามด้วยคอลัมน์ที่เป็นช่วง (`>=`, `BETWEEN`) หรือใช้เรียงลำดับ

```sql
ALTER TABLE orders
  ADD INDEX idx_orders_status_created (status, created_at);
```

เมื่อ index เรียงเป็น `(status, created_at)` MySQL กระโดดไปที่กลุ่ม `paid` แล้วไล่ `created_at` ที่เรียงไว้แล้วได้ทันที `Using filesort` หายไป และ `rows` ลดลงจากหลักแสนเหลือหลักสิบ ถ้าสลับลำดับเป็น `(created_at, status)` index จะช่วยได้น้อยกว่ามาก เพราะเงื่อนไขช่วงวันที่ตัดการใช้คอลัมน์ถัดไป

ข้อควรระวัง: อย่าใส่ index ทุกคอลัมน์ ทุก index ทำให้ `INSERT` และ `UPDATE` ช้าลง และกินพื้นที่ disk ผมจะเพิ่ม index ก็ต่อเมื่อมี query จริงที่ได้ประโยชน์ และลบ index ที่ซ้ำซ้อนทิ้ง เช่น ถ้ามี `(status, created_at)` แล้ว index เดี่ยวบน `status` ก็มักไม่จำเป็น

## 4. Covering index สำหรับ query ที่ถูกเรียกบ่อย

ถ้า query ดึงแค่ไม่กี่คอลัมน์ และคอลัมน์เหล่านั้นอยู่ใน index ครบ MySQL ไม่ต้องกลับไปอ่านแถวจริงในตารางเลย ใน `EXPLAIN` จะเห็น `Using index` ใน `Extra`

เหมาะกับ query ประเภทนับจำนวนหรือ summary บน dashboard เช่น นับ order ต่อสถานะต่อวัน ผมใช้เทคนิคนี้อย่างเลือกสรร เพราะ index ที่กว้างเกินไปก็มีต้นทุนเหมือนกัน

## 5. กำจัด N+1 ในชั้น application

query ช้าไม่ได้อยู่ใน SQL เสมอไป หลายครั้งตัวการคือ ORM ที่ยิง query ทีละแถว ใน Laravel ตัวอย่างคลาสสิกคือ

```php
// N+1: 1 query สำหรับ orders + อีก N query สำหรับ customer
$orders = Order::where('status', 'paid')->latest()->take(50)->get();
foreach ($orders as $order) {
    echo $order->customer->name;
}

// แก้ด้วย eager loading: เหลือ 2 query
$orders = Order::with('customer:id,name')
    ->where('status', 'paid')
    ->latest()
    ->take(50)
    ->get();
```

วิธีจับ N+1 ที่ง่ายที่สุดคือเปิด query log ระหว่างพัฒนาแล้วนับจำนวน query ต่อ request ถ้าหน้าจอหนึ่งยิง query เป็นร้อย แทบแน่นอนว่ามี N+1 ซ่อนอยู่ ใน Laravel รุ่นใหม่ยังสั่ง `Model::preventLazyLoading()` ในสภาพแวดล้อม development เพื่อให้ error ทันทีเมื่อเกิด lazy loading ได้

## 6. เลือกเฉพาะคอลัมน์ที่ใช้

`SELECT *` ดูไม่มีพิษภัย แต่ถ้าตารางมีคอลัมน์ข้อความยาวหรือ JSON การดึงทุกคอลัมน์ทำให้ส่งข้อมูลข้าม network มากเกินจำเป็น และทำให้ covering index ใช้ไม่ได้ ผมจึงระบุคอลัมน์ทุกครั้งใน query ที่ถูกเรียกบ่อย

## 7. วัดซ้ำหลังแก้

หลังเพิ่ม index หรือแก้โค้ด ผมกลับไปวัดด้วยวิธีเดียวกับ baseline ทุกครั้ง บางครั้ง index ใหม่ทำให้ query หนึ่งเร็วขึ้นแต่อีก query กลับช้าลง เพราะ optimizer เปลี่ยนแผน การวัดซ้ำคือสิ่งเดียวที่บอกได้

ผมยังทำ checklist สั้น ๆ ก่อน deploy การเปลี่ยน index บน production:

- ลอง `ALTER TABLE` บนสำเนาข้อมูลขนาดใกล้เคียงก่อน เพื่อรู้ว่าใช้เวลานานแค่ไหน
- เลือกช่วงเวลาที่ผู้ใช้น้อย
- เตรียมคำสั่ง `DROP INDEX` ไว้เป็น rollback

## สรุป

การลด latency ได้กว่า 40% ไม่ได้มาจากเทคนิคลับ แต่มาจากการทำพื้นฐานให้ครบตามลำดับ: วัด baseline, อ่าน `EXPLAIN`, ออกแบบ composite index ให้ตรงกับรูปแบบ query, ใช้ covering index กับ query ที่ถูกเรียกบ่อย, กำจัด N+1 ในโค้ด, เลือกเฉพาะคอลัมน์ที่ใช้ และวัดซ้ำทุกครั้ง ถ้าคุณเพิ่งเริ่ม ให้เริ่มจาก query ที่ถูกเรียกบ่อยที่สุดสักสามตัว ผลที่ได้มักคุ้มกว่าการไล่แก้ทุกอย่างพร้อมกัน บทเรียนอื่น ๆ จากปีที่ผ่านมาผมเล่าไว้ใน [บทเรียนจากปี 2025](/blog/lessons-from-2025-full-stack)
