ช่วงหนึ่งผมเชื่อว่าถ้า AI ทำงานผิด แปลว่า prompt ยังไม่ละเอียดพอ ผมจึงเขียน prompt ให้ยาวขึ้นเรื่อย ๆ ใส่ข้อห้าม ใส่ตัวอย่าง ใส่บริบท จนบางไฟล์ยาวหลายหน้า ผลที่ได้ไม่ได้ดีขึ้นตามความยาว บางครั้งแย่ลงด้วยซ้ำ สิ่งที่เปลี่ยนผลลัพธ์จริงคือ discipline ไม่ใช่ prompt ที่ยาวขึ้น โดยเฉพาะโครงสร้างสามส่วน คือ mission, checklist และ verification

นี่คือแนวคิดที่กลายมาเป็นแกนของ Kasidit framework ที่ผมทำเป็น open source

## ทำไม prompt ยาวไม่ได้ผล

prompt ยาวมีปัญหาสามข้อ

- **คำสั่งชนกันเอง** ยิ่งเขียนมากยิ่งมีโอกาสที่สองบรรทัดจะขัดกัน และ model ต้องเลือกเอง
- **ความสำคัญถูกเจือจาง** เมื่อทุกอย่างเป็น "สำคัญมาก" ก็ไม่มีอะไรสำคัญ
- **ไม่มีจุดตรวจ** prompt บอกว่าต้องทำอะไร แต่ไม่ได้บอกว่าจะรู้ได้อย่างไรว่าทำเสร็จแล้วและถูกต้อง

ข้อสุดท้ายคือหัวใจ ปัญหาส่วนใหญ่ของ AI coding ไม่ได้เกิดจาก model ไม่รู้ว่าต้องทำอะไร แต่เกิดจาก model ประกาศว่า "เสร็จแล้ว" ทั้งที่ยังไม่ได้ตรวจ

## ส่วนที่ 1: Mission

mission คือขอบเขตงานที่เขียนสั้นและชัด ไม่ใช่คำอธิบายยาว ผมใช้โครงแบบนี้

```markdown
## Mission
Goal: Fix duplicate rows in the orders export CSV
Scope: app/Exports/OrdersExport.php only
Out of scope: UI, other exports, refactoring
Done when:
  - Export of a test order with 3 lines returns exactly 3 rows
  - Existing export tests still pass
Risk: Low (read-only export, no schema change)
```

สังเกตว่ามี "Out of scope" และ "Done when" สองบรรทัดนี้มีค่ามากกว่าย่อหน้าบริบทยาว ๆ เพราะมันบอก model ว่าต้องหยุดตรงไหน AI ที่ไม่มีขอบเขตชัดมักแก้เกินกว่าที่ขอ ซึ่งเป็นต้นเหตุของบั๊กใหม่ ผมเขียนเรื่องการให้ AI ปฏิเสธงานที่ขอบเขตไม่ชัดไว้ใน [AI agent ควรปฏิเสธ scope ที่คลุมเครือ](/blog/ai-agent-refuse-vague-scope)

## ส่วนที่ 2: Checklist

checklist คือรายการสิ่งที่ต้องตรวจทุกครั้งสำหรับงานประเภทนั้น ไม่ต้องเขียนใหม่ทุกงาน แต่ใช้ซ้ำได้ ตัวอย่าง checklist สำหรับงานแก้ฐานข้อมูล

- migration ย้อนกลับได้หรือไม่
- มี index สำหรับคอลัมน์ที่ใช้ใน `WHERE` ใหม่หรือไม่
- การเปลี่ยนแปลงกระทบโค้ดที่อ่านคอลัมน์เดิมหรือไม่
- ทดสอบกับข้อมูลขนาดใกล้ production แล้วหรือยัง

ข้อดีของ checklist คือมันแยกออกจาก prompt ของงาน prompt จึงสั้นลง และ checklist ก็ดีขึ้นเรื่อย ๆ ทุกครั้งที่เจอปัญหาใหม่ เราแค่เพิ่มหนึ่งบรรทัด ความรู้สะสมอยู่ในที่เดียว แทนที่จะกระจายอยู่ใน prompt หลายสิบไฟล์ เรื่องการใช้ checklist ในการรีวิวโค้ด ผมขยายไว้ใน [AI code review checklists](/blog/ai-code-review-checklists)

## ส่วนที่ 3: Verification

verification คือหลักฐานว่างานเสร็จจริง กฎของผมคือ runtime เป็นผู้ตัดสิน ไม่ใช่ความมั่นใจของ model

- ถ้าแก้บั๊ก ต้องมีการรันที่แสดงว่าบั๊กหายแล้ว
- ถ้าเพิ่มฟีเจอร์ ต้องมี test หรืออย่างน้อยผลการรันจริง
- ถ้าตรวจไม่ได้ ต้องบอกตรง ๆ ว่ายังไม่ได้ตรวจ

ผมให้ AI ติด confidence label กับข้อสรุปของมันด้วย เช่น verified เมื่อรันแล้วเห็นผล หรือ inferred เมื่ออนุมานจากการอ่านโค้ด การแยกแบบนี้ทำให้ผมรู้ทันทีว่าส่วนไหนต้องตรวจเพิ่ม

## Hooks: ทำให้ discipline ไม่ต้องพึ่งความจำ

discipline ที่พึ่งความจำของคนหรือของ model จะหลุดในวันที่เหนื่อย ผมจึงใช้ hooks ของ Claude Code บังคับบางกฎให้เป็นอัตโนมัติ เช่น ห้าม commit เองโดยไม่ขออนุญาต หรือเตือนเมื่อมีคำสั่งลบข้อมูล กฎที่ถูกบังคับด้วยเครื่องมือเชื่อถือได้กว่ากฎที่เขียนไว้ใน prompt เสมอ

## ผลที่วัดได้

ผมทดสอบ Kasidit กับ SWE-bench เทียบกับการไม่ใช้ framework ใด ๆ ผลคือแก้โจทย์ได้ 75% เทียบกับ 63% โดยใช้ model เดียวกัน ความต่างไม่ได้มาจาก prompt ที่ยาวขึ้น แต่มาจากโครงสร้างที่บังคับให้กำหนดขอบเขต ตรวจตาม checklist และยืนยันผลก่อนประกาศว่าเสร็จ รายละเอียดอยู่ที่ [kasi.kasion.dev](https://kasi.kasion.dev)

## เริ่มใช้ได้พรุ่งนี้

ไม่ต้องติดตั้งอะไรก็เริ่มได้

1. ก่อนสั่งงาน AI เขียน Goal, Scope, Out of scope และ Done when ให้ครบสี่บรรทัด
2. สร้างไฟล์ checklist หนึ่งไฟล์สำหรับประเภทงานที่ทำบ่อยที่สุด
3. ไม่ยอมรับคำว่า "เสร็จแล้ว" จนกว่าจะเห็นผลการรันจริง
4. ทุกครั้งที่เจอปัญหาซ้ำ เพิ่มหนึ่งบรรทัดใน checklist แทนการเพิ่มย่อหน้าใน prompt

## สรุป

prompt ที่ยาวขึ้นให้ผลลัพธ์ที่ไม่แน่นอน แต่ discipline ให้ผลลัพธ์ที่ทำซ้ำได้ แยกงานเป็น mission ที่มีขอบเขตชัด checklist ที่สะสมความรู้ และ verification ที่ใช้ runtime เป็นผู้ตัดสิน แล้วใช้เครื่องมือบังคับกฎที่สำคัญ คุณจะได้ AI ที่ทำงานแบบมืออาชีพมากขึ้นโดยไม่ต้องเขียน prompt ยาวขึ้นแม้แต่บรรทัดเดียว
