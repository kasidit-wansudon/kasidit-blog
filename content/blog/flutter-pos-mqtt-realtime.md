ก่อนจะมาทำระบบหลังบ้านเต็มตัว ผมเคยทำงานเป็น Mobile Developer ที่ SmilePOS ช่วงกลางปี 2023 ถึงต้นปี 2024 งานหลักคือระบบ POS ที่เขียนด้วย Flutter รันบน 6 แพลตฟอร์ม และต้อง sync ข้อมูลระหว่างเครื่องแบบ real-time ด้วย MQTT ช่วงปลายปีแบบนี้ผมเลยอยากมองย้อนว่าการทำ Flutter POS กับ MQTT สอนอะไรผมบ้าง ทั้งเรื่องสถาปัตยกรรมและนิสัยการทำงาน

## ทำไม POS ต้อง real-time

ร้านที่มีหลายเครื่องต้องเห็นข้อมูลตรงกันแทบทันที เช่น เครื่องหน้าร้านรับ order แล้วครัวต้องเห็น หรือเมื่อสินค้าหมดที่เครื่องหนึ่ง เครื่องอื่นต้องไม่ขายต่อ ถ้าใช้วิธีให้ทุกเครื่องถาม server เป็นระยะ (polling) จะช้าและเปลือง network มาก

MQTT เหมาะกับโจทย์นี้เพราะเป็น protocol แบบ publish/subscribe ที่เบา ออกแบบมาสำหรับอุปกรณ์ที่ network ไม่เสถียร เครื่องแต่ละเครื่อง subscribe เฉพาะ topic ที่สนใจ และ broker ส่งข้อความให้ทันทีเมื่อมีการเปลี่ยนแปลง

## ทำไม Flutter และ 6 แพลตฟอร์ม

ร้านค้าใช้อุปกรณ์หลากหลาย ทั้งแท็บเล็ต มือถือ และเครื่องคอมพิวเตอร์ การมี codebase เดียวที่ build ได้หลายแพลตฟอร์มช่วยให้ทีมเล็กดูแลได้ไหว Flutter ทำเรื่องนี้ได้ดี แต่ "codebase เดียว" ไม่ได้แปลว่า "ไม่มีงานเฉพาะแพลตฟอร์ม" เรื่องอย่างการเชื่อมเครื่องพิมพ์ใบเสร็จ สิทธิ์การเข้าถึง หรือพฤติกรรมเมื่อแอปไปอยู่เบื้องหลัง ต่างกันในแต่ละแพลตฟอร์มเสมอ

## ออกแบบ topic ให้เป็นระเบียบ

สิ่งที่ผมเรียนรู้เร็วที่สุดคือ ถ้า topic ไม่มีโครงสร้างที่ชัด ระบบจะกลายเป็นมั่วภายในไม่กี่เดือน รูปแบบที่ผมคิดว่าดีคือเรียงจากกว้างไปแคบ

```text
pos/{shopId}/orders/created
pos/{shopId}/orders/{orderId}/status
pos/{shopId}/stock/{productId}
pos/{shopId}/devices/{deviceId}/presence
```

โครงสร้างแบบนี้ทำให้เครื่องในร้านหนึ่ง subscribe `pos/{shopId}/#` แล้วได้ทุกอย่างของร้านตัวเอง และไม่มีทางเห็นข้อมูลร้านอื่น ถ้ามีการตั้งสิทธิ์ที่ broker ให้ตรงกับโครงสร้างนี้ด้วย

## ตัวอย่างการเชื่อมต่อใน Flutter

ฝั่ง Flutter ผมใช้ package `mqtt_client` ตัวอย่างแบบย่อของการเชื่อมต่อและ subscribe มีหน้าตาประมาณนี้

```dart
final client = MqttServerClient('broker.example.com', deviceId)
  ..port = 8883
  ..secure = true
  ..keepAlivePeriod = 30
  ..autoReconnect = true;

client.connectionMessage = MqttConnectMessage()
    .withClientIdentifier(deviceId)
    .startClean();

await client.connect(username, password);
client.subscribe('pos/$shopId/#', MqttQos.atLeastOnce);

client.updates!.listen((events) {
  final msg = events.first.payload as MqttPublishMessage;
  final payload =
      MqttPublishPayload.bytesToStringAsString(msg.payload.message);
  handleMessage(events.first.topic, payload);
});
```

จุดที่ควรสังเกตคือ `autoReconnect` และ `keepAlivePeriod` ในร้านจริง Wi-Fi หลุดบ่อยกว่าที่คิด แอปต้องกลับมาเชื่อมต่อเองโดยที่พนักงานไม่ต้องทำอะไร

## QoS: เลือกให้ตรงกับความสำคัญของข้อความ

MQTT มี QoS สามระดับ ผมใช้หลักง่าย ๆ

- **QoS 0** สำหรับข้อมูลที่หายได้ เช่น สถานะออนไลน์ของเครื่อง เพราะเดี๋ยวก็ส่งใหม่
- **QoS 1** สำหรับ order และสต็อก ซึ่งต้องถึงอย่างน้อยหนึ่งครั้ง

QoS 1 หมายความว่าข้อความอาจมาซ้ำได้ ฝั่งรับจึงต้อง idempotent เช่น ทุก order มี id ที่สร้างจากเครื่องต้นทาง ถ้าได้รับ id เดิมซ้ำก็ข้ามไป บทเรียนนี้ผมใช้ต่อมาในงาน webhook อีกหลายระบบ

## Offline คือสภาพปกติ ไม่ใช่ข้อยกเว้น

POS ต้องขายได้แม้ network ล่ม ร้านไม่สามารถบอกลูกค้าว่า "รออินเทอร์เน็ตกลับมาก่อน" ได้ แนวทางที่ผมคิดว่าถูกต้องคือ

1. บันทึกทุกรายการลง database ในเครื่องก่อนเสมอ
2. ใส่ไว้ในคิวที่รอส่ง
3. เมื่อเชื่อมต่อได้ ค่อยส่งตามลำดับและลบออกจากคิวเมื่อได้รับการยืนยัน

ข้อดีคือแอปทำงานเหมือนกันทั้งตอนออนไลน์และออฟไลน์ ความซับซ้อนย้ายไปอยู่ที่การ sync ซึ่งควบคุมได้ง่ายกว่า

## Google Maps กับ delivery zone

อีกส่วนที่ผมทำคือการกำหนดพื้นที่จัดส่งด้วย Google Maps ร้านวาดขอบเขตพื้นที่บนแผนที่ แล้วระบบเช็กว่าที่อยู่ลูกค้าอยู่ในพื้นที่ไหน บทเรียนจากส่วนนี้คือ ข้อมูลเชิงพื้นที่ควรถูกตรวจซ้ำฝั่ง server ด้วย ไม่ควรเชื่อผลจากฝั่ง client อย่างเดียว

## สิ่งที่ผมได้เรียนรู้

- **ออกแบบสำหรับความล้มเหลว** network, เครื่องพิมพ์ และอุปกรณ์จะพังในเวลาที่แย่ที่สุดเสมอ
- **ข้อความซ้ำต้องไม่ทำให้ข้อมูลผิด** idempotency เป็นเรื่องพื้นฐาน ไม่ใช่ของเสริม
- **ทดสอบบนอุปกรณ์จริง** emulator ไม่เคยจำลองร้านที่ Wi-Fi อ่อนได้เหมือนจริง
- **cross-platform ประหยัดเวลา แต่ไม่ได้ลบงานเฉพาะแพลตฟอร์ม** ต้องเผื่อเวลาไว้เสมอ

## สรุป

การทำ Flutter POS ที่ sync แบบ real-time ด้วย MQTT บน 6 แพลตฟอร์ม สอนให้ผมคิดเรื่องระบบกระจายตั้งแต่ยังเป็น developer รุ่นเล็ก: ออกแบบ topic ให้เป็นระเบียบ, เลือก QoS ตามความสำคัญ, ทำให้ฝั่งรับ idempotent และถือว่า offline เป็นสภาพปกติ หลักเหล่านี้ยังใช้ได้กับงานหลังบ้านที่ผมทำทุกวันนี้ แม้จะไม่ได้เขียน Flutter แล้วก็ตาม
