ตอนเป็น Technical Lead ผมดูแลทีมห้าคน ฝั่งที่ทำงานกับโค้ดโดยตรงมีสี่คนรวมผม (2 programmer, 1 QA และผม) ที่เหลือดูแล helpdesk กับ infra แต่ระบบที่ต้องดูแลมีมากกว่า 6 ระบบ คำถามที่ผมต้องตอบทุกวันคือ จะบริหารทีม dev เล็กร่วมกับ AI agent อย่างไรให้ได้งานเยอะขึ้นโดยคุณภาพไม่ตก บทความนี้สรุปสิ่งที่ผมใช้จริง: กติกากลาง การแบ่งงาน และ review flow

## ปัญหาของการปล่อยให้แต่ละคนใช้ AI ตามใจ

ช่วงแรกทุกคนใช้ AI กันเอง ผลที่ได้คือ:

- โค้ดสไตล์ไม่เหมือนกัน เพราะแต่ละคนสั่ง AI ต่างกัน
- AI แก้ไฟล์เกินขอบเขตที่ขอ แล้วไม่มีใครสังเกต
- บางคนเชื่อ AI ทั้งหมด บางคนไม่ใช้เลย ผลงานต่างกันมาก
- bug แปลก ๆ ที่ AI แต่งขึ้นเอง หรือ AI วนแก้ปัญหาที่ไม่มีอยู่จริง

ปัญหาไม่ได้อยู่ที่ AI แต่อยู่ที่ไม่มีกติกาเดียวกัน

## กติกากลางที่ทุกคนใช้ร่วมกัน

ผมเขียนกติกาไว้ในไฟล์เดียวที่อยู่ใน repo ทุกตัว (สำหรับ Claude Code คือ `CLAUDE.md`) ทั้งคนและ AI อ่านไฟล์เดียวกัน ตัวอย่างโครงสร้าง:

```markdown
# Team rules (ใช้กับทั้งคนและ AI)

## Scope
- แก้เฉพาะสิ่งที่ ticket ขอ ห้าม refactor นอก scope
- ถ้า scope ไม่ชัด ให้ถามก่อน อย่าเดา

## Code
- PHP: PSR-12, Laravel conventions, ห้าม raw SQL ที่ต่อ string จาก input
- Vue: Composition API, ข้อความทุกอันผ่าน i18n
- Comment และชื่อตัวแปรเป็นภาษาอังกฤษ

## Safety
- ห้าม commit secret / .env
- migration ต้อง reversible และมี down()
- ห้ามรันคำสั่งที่ลบข้อมูลโดยไม่ยืนยัน

## Output
- ทุกคำตอบของ AI ต้องระบุ confidence: verified / likely / guess
- ระบุไฟล์ที่แก้ทั้งหมดท้ายคำตอบ
```

กติกาเรื่อง confidence label ช่วยได้มาก เพราะทำให้คนรีวิวรู้ทันทีว่าส่วนไหน AI รันทดสอบแล้ว ส่วนไหนแค่เดา แนวคิดทั้งหมดนี้ผมรวบรวมเป็น open-source framework ชื่อ Kasidit ที่ https://kasi.kasion.dev

## AI ทำอะไร คนทำอะไร

ผมแบ่งงานตามความเสี่ยงและความต้องการบริบททางธุรกิจ:

**ให้ AI ทำเป็นหลัก**
- scaffold CRUD, form, validation ตาม pattern ที่มีอยู่แล้ว
- เขียน test จากโค้ดที่มีอยู่
- แปลข้อความ i18n รอบแรก (คนตรวจทีหลัง)
- อ่าน log หรือ stack trace แล้วเสนอสาเหตุที่เป็นไปได้
- เขียนร่างเอกสาร เช่น deploy-list หรือ handover

**ให้คนทำเป็นหลัก**
- คุยกับผู้ใช้และแปลง requirement เป็น scope
- ออกแบบ schema และ data flow ข้ามระบบ
- ตัดสินใจเรื่อง trade-off เช่น จะตัดฟีเจอร์ไหนออก
- deploy และ rollback บน production
- ทุกอย่างที่เกี่ยวกับสิทธิ์ การเงิน และข้อมูลส่วนบุคคล

หลักง่าย ๆ คือ AI เก่งเรื่อง "ทำให้เร็ว" คนต้องรับผิดชอบเรื่อง "ทำสิ่งที่ถูก"

## Review flow ที่ใช้จริง

โค้ดจาก AI ต้องผ่าน flow เดียวกับโค้ดที่คนเขียน ไม่มีข้อยกเว้น:

1. **Developer รีวิวตัวเองก่อน** อ่าน diff ทุกบรรทัดที่ AI สร้าง ถ้าอธิบายไม่ได้ว่าโค้ดบรรทัดนั้นทำอะไร ห้ามเปิด merge request
2. **AI review ด้วย checklist** ให้ AI ตัวที่สองรีวิว diff ตาม checklist ที่ตายตัว (security, database, state) ไม่ใช่สั่งว่า "ช่วยรีวิวหน่อย" ดูตัวอย่าง checklist ใน [AI code review checklists](/blog/ai-code-review-checklists)
3. **Peer review โดยคน** อย่างน้อยหนึ่งคน โฟกัสที่ logic ทางธุรกิจและผลกระทบต่อระบบอื่น
4. **QA ทดสอบบน staging** ตาม test case ที่เขียนจาก ticket ไม่ใช่จากโค้ด
5. **Deploy ด้วย deploy-list** โดยคนเท่านั้น

ขั้นที่ 1 สำคัญที่สุดและถูกข้ามบ่อยที่สุด ผมจึงถามในการรีวิวเสมอว่า "บรรทัดนี้ทำไมต้องมี" ถ้าตอบว่า "AI ใส่มา" แปลว่ายังไม่พร้อม

## วัดผลอย่างไร

ผมไม่วัดจากจำนวนบรรทัดหรือจำนวน commit เพราะ AI ทำให้ตัวเลขพวกนี้พองได้ง่าย สิ่งที่ผมดูคือ:

- ticket ปิดได้ต่อสัปดาห์ และเวลาตั้งแต่เปิดจนขึ้น production
- จำนวน rollback และ hotfix หลัง deploy
- จำนวนรอบที่ MR ต้องแก้หลัง review

ถ้า ticket ปิดเร็วขึ้นแต่ rollback เพิ่ม แปลว่ากติกาหรือ review flow มีช่องโหว่ ต้องกลับไปแก้ที่กติกา ไม่ใช่โทษคน

## สรุป

การบริหารทีม dev เล็กร่วมกับ AI agent ให้ได้ผลขึ้นกับสามอย่าง: กติกากลางที่ทั้งคนและ AI อ่านไฟล์เดียวกัน การแบ่งงานที่ให้ AI ทำงานซ้ำและให้คนตัดสินใจ และ review flow ที่โค้ดจาก AI ไม่ได้รับข้อยกเว้น ทีมสี่คนจะทำงานได้เหมือนทีมใหญ่กว่า ถ้ามีวินัยร่วมกัน
