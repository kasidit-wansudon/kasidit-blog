ตอนเริ่มใช้ Claude Code ผมใช้ model ที่ดีที่สุดกับทุกงาน ตั้งแต่วางแผนสถาปัตยกรรมไปจนถึงค้นหาว่าฟังก์ชันหนึ่งอยู่ไฟล์ไหน ผลคือได้คุณภาพดี แต่ช้าและเปลืองโดยไม่จำเป็น หลังจากลองผิดลองถูกมาพักหนึ่ง ผมแบ่งงานตาม model tiers แบบง่าย ๆ คือ Opus วางแผน Sonnet ลงมือ Haiku ค้นหา และพบว่ามันสมดุลระหว่างคุณภาพกับต้นทุนได้ดีกว่ามาก

โพสต์นี้ไม่ได้อ้างตัวเลขราคา เพราะเปลี่ยนตามเวลา ให้ดูจากเอกสารทางการ แต่หลักการเลือกใช้ยังคงเดิม

## ทำไมต้องแบ่ง tier

งานเขียนซอฟต์แวร์ไม่ได้ยากเท่ากันทุกขั้น ลองแยกดู

- **วางแผน** ต้องเข้าใจภาพรวม ชั่งน้ำหนัก trade-off มองเห็นความเสี่ยง งานนี้ผิดแล้วแพง เพราะทุกขั้นถัดไปสร้างบนแผนนี้
- **ลงมือ** เมื่อแผนชัดแล้ว การเขียนโค้ดตามแผนเป็นงานที่ต้องการความแม่นยำ แต่ไม่ต้องคิดลึกเท่าการวางแผน
- **ค้นหา** หาไฟล์ อ่านโครงสร้าง grep หา pattern งานนี้ปริมาณมาก แต่แต่ละครั้งง่าย

ถ้าใช้ model ใหญ่ที่สุดกับทั้งสามขั้น เรากำลังจ่ายราคาของการคิดลึกให้กับงานที่ไม่ต้องคิดลึก

## Opus: วางแผนและตัดสินใจ

ผมใช้ Opus เมื่อ

- งานแตะหลายไฟล์ หรือเปลี่ยนโครงสร้างข้อมูล
- ต้องออกแบบก่อนเขียน เช่น schema ใหม่ หรือ flow การย้ายระบบ
- ต้องหาต้นเหตุของบั๊กที่ซับซ้อนและไล่มาหลายรอบแล้วยังไม่เจอ
- ต้องรีวิวงานด้านความปลอดภัยหรือการเปลี่ยนแปลงที่ย้อนกลับยาก

ผลลัพธ์ที่ผมขอจาก Opus คือแผนที่มีรายการไฟล์ ลำดับขั้นตอน ความเสี่ยง และเงื่อนไขว่าเมื่อไรถือว่าเสร็จ ไม่ใช่โค้ด

## Sonnet: ลงมือตามแผน

Sonnet เป็นตัวหลักที่ผมใช้มากที่สุด งานที่เหมาะคือ

- เขียนโค้ดตามแผนที่ชัดแล้ว
- แก้บั๊กที่รู้ต้นเหตุแล้ว
- เขียน test, migration, หรือปรับ UI ตามที่กำหนด

กุญแจคือแผนต้องชัดพอ ถ้า Sonnet ต้องเดาเยอะ แปลว่าขั้นวางแผนยังไม่เสร็จ ให้กลับไปที่ Opus แทนการให้ Sonnet เดาไปเรื่อย ๆ

## Haiku: ค้นหาและงานปริมาณมาก

Haiku เร็วและประหยัด เหมาะกับ

- ค้นหาว่า function หรือ config อยู่ไฟล์ไหน
- สรุปโครงสร้างโฟลเดอร์
- ตรวจ pattern ซ้ำ ๆ ในหลายไฟล์
- งานจัดหมวดหมู่หรือดึงข้อมูลแบบมีโครงสร้าง

การให้ Haiku ไปค้นหาแล้วส่งสรุปกลับมา ยังช่วยให้ context ของ model หลักสะอาด เพราะไม่ต้องอ่านผลการค้นหายาว ๆ ทั้งหมดเอง

## ตั้งค่าใน Claude Code ด้วย subagents

Claude Code ให้กำหนด subagent พร้อม model ที่ใช้ได้ในไฟล์ markdown ที่มี frontmatter ตัวอย่าง subagent สำหรับค้นหา

```markdown
---
name: code-searcher
description: Find files, functions, and config locations. Use for any "where is X" question. Returns paths and short excerpts only.
tools: Read, Grep, Glob
model: haiku
---

You locate code. Search broadly, then narrow down.
Return: file paths with line numbers and a one-line note each.
Do not edit files. Do not propose fixes.
```

และ subagent สำหรับวางแผน

```markdown
---
name: planner
description: Plan before code for changes touching more than 2 files. Returns steps, file list, risks, and done criteria. Does not write code.
tools: Read, Grep, Glob
model: opus
---

Produce a numbered plan with: goal, files to change, order of steps,
risks, and how to verify each step. Mark assumptions as inferred.
```

จากนั้น session หลักที่รันด้วย Sonnet จะส่งงานค้นหาให้ `code-searcher` และงานวางแผนให้ `planner` ตามความเหมาะสม รูปแบบนี้ผมใส่ไว้ใน Kasidit framework เป็นคำสั่ง cascade ให้ใช้ได้ทันที ดูได้ที่ [kasi.kasion.dev](https://kasi.kasion.dev)

## เกณฑ์เลือกแบบเร็ว

เวลาไม่แน่ใจ ผมถามตัวเองสามข้อ

1. **ถ้าผิด ต้องแก้กี่ไฟล์** ถ้าหลายไฟล์หรือย้อนกลับยาก ใช้ tier สูง
2. **งานนี้ต้องตัดสินใจ หรือแค่ทำตาม** ตัดสินใจใช้ Opus ทำตามใช้ Sonnet
3. **ต้องทำซ้ำกี่ครั้ง** งานที่ทำซ้ำเยอะและง่าย ใช้ Haiku

## ข้อควรระวัง

- **อย่าประหยัดผิดที่** การใช้ model เล็กวางแผนแล้วได้แผนผิด จะเสียมากกว่าค่า token ที่ประหยัดได้หลายเท่า
- **ตรวจผลของ tier ล่างเสมอ** Haiku อาจค้นไม่ครบ ถ้าผลสำคัญให้ยืนยันอีกครั้ง
- **ไม่ต้องแบ่งงานเล็กเกินไป** งานแก้บรรทัดเดียวไม่จำเป็นต้องผ่านสาม tier การ delegate เองก็มีต้นทุน

## สรุป

model tiers ไม่ใช่เรื่องของการประหยัดอย่างเดียว แต่เป็นการจับคู่ความสามารถกับความยากของงาน ให้ Opus วางแผนและตัดสินใจเรื่องที่ผิดแล้วแพง ให้ Sonnet ลงมือตามแผนที่ชัด และให้ Haiku ค้นหาและทำงานปริมาณมาก ตั้งค่าเป็น subagent ครั้งเดียวแล้วใช้ได้ทุกวัน คุณจะได้ทั้งคุณภาพที่ดีขึ้นและต้นทุนที่สมเหตุสมผล
